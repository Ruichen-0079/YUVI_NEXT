# 事件与用语约定

本文件只收两类东西：

- **写进档案的事件的含义：** 档案只追加，一个事件种类的含义一旦写进历史，就不能再改；
- **容易被混淆、混淆后会改变架构的几组区分。**

它不是通用术语表。超过一页，就删到一页以内。

## 1. 事件种类

| `class/kind`        | 记录了什么                                                                                                                 | 不表示什么                                 | 引入 |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ | ---- |
| `experience/heard`  | 一条消息已被接收并入档                                                                                                     | 已被理解，或已被回复                       | P1   |
| `act/reply_attempt` | YUVI 的一条回复开始对外发送（第一个增量推出之前写入）                                                                      | 对方收到了任何内容                         | P1   |
| `act/said`          | 一条回复完整生成，且已尝试全部发送                                                                                         | 对方收到或读到                             | P1   |
| `control/error`     | 某条 `heard` 的回合以失败或中断结束                                                                                        | 沉默；YUVI 的选择                          | P1   |
| `act/silent`        | YUVI 在这一回合选择不回复（通过 `stay_silent`）；`content` 为它给出的理由，可为空，不对外发送                              | 失败；对方知道它在沉默                     | P2   |
| `control/restored`  | 此档案由一份快照恢复而来：在它之前的事件来自该快照（`meta.through_seq`、`meta.snapshot_sha256`），之后的事件发生在恢复之后 | 原档案在快照之后没有别的事件；有事件被删除 | P3   |
| `inner/wrote`       | YUVI 写下的文字。P4 中只在整理时产生：`meta.material` 为它这次读到的本场景对话事件范围（`from_seq`–`through_seq`）；`content` 为它写下的全部文字，可以为空（读过，没有写）；`meta.finish_reason="length"` 表示写到长度上限时停止 | 对材料的摘要或准确记录；它的全部记忆；任何类型 | P4   |
| `act/checked`       | YUVI 在一个回合中调用 `check` 查阅档案原文；`meta.arguments` 为查询条件，`meta.result_seqs` 为返回给它的事件；`meta.invalid=true` 表示参数无效、没有查询。P8 起，`meta.rules`、`engine`、`mode` 说明这次怎样选取，`meta.rank_seqs` 为按选取顺序排列的候选（最多 100 个） | 它相信或采用了这些内容；档案是它全部经历的完整记录；`rank_seqs` 中的事件被返回给了它 | P4   |
| `control/unconsolidated` | 一批对话事件（`meta.material`）没有经过整理，就因积压上限离开了原文窗口                                              | 事件被删除；它从未看到过它们（它们曾在对话上下文中） | P4   |
| `control/presented` | 程序为一次模型请求组装好了内容，即将交给请求发送；`meta` 为呈现清单（用途、步骤、各部分引用的档案事件与长度、组装规则版本、请求参数、消息摘要，见 P7 §3.2）；对话请求的 `reply_to` 为当前 `heard` | 请求已发出或对方已收到；模型读了、注意到、采纳或使用了其中任何内容 | P7 |

`control/error` 的 `meta.outcome` 有三个取值：

- `not_sent`：尚未开始对外发送；
- `partial`：`content` 中的文本已写出到对外连接，随后失败；不表示对方收到其中任何部分；
- `unknown`：已开始发送，但进程中断，已发出多少不可知。

**规则：**

- 种类只增不改。
- 要改变一个种类的含义，就新增一个种类，旧种类在本表中标注“停用于 P<n>”，但不删除。
- 代码写入档案的每个 `class/kind`，都必须先出现在本表中。

## 2. 必须区分的概念

- **档案 ≠ 记忆。**
  - 档案是程序写下的、关于发生过什么的记录（事件表），只包含被记录下来的事件；它不是 YUVI 全部经历的完整记录。
  - 记忆是它自己整理形成的回忆，可以不准确（P4 起）。P4 中，它整理时写下的文字（`inner/wrote`）是记忆中说得出的那部分的候选载体，不是记忆的定义；程序不判断它写得对不对。
  - 代码中 `memory`、`recall` 只能指后者；读取档案原文叫 `events` 或 `check`。
- **查得到 ≠ 被纠正。** 更正入档后可以被 `check` 查到；它是否相信、是否改写自己的文字，是它的事，程序不保证，也不替它判断哪个说法有效。
- **发送尝试 ≠ 送达。** 程序只记录它做了什么。对方是否收到，只能由独立的回执证明。
- **呈现 ≠ 被使用。** `control/presented` 只说明程序把什么放进了一次请求；请求是否发出、是否被接收，要看之后的事件；模型是否读了或用了，档案不能证明。
- **沉默 ≠ 失败。** 沉默是 YUVI 的行为（`act/silent`），失败是 `control/error`。二者不能互相替代。
- **内心记录（`inner`）不分类型。** `inner` 只有一个 kind：`wrote`，不再增加；也不加情绪、意图、重要性等字段。
- **关系 ≠ 意义。**
  - 程序记录可核验的关系：谁、何时、在哪、回复谁、是否送达、谁能看到。
  - 意义由模型给出。
  - 程序侧任何判断“这句话是什么意思”的代码，都需要 P 文件明确授权。
- **研究对象不以字段冒充。** 心境、潜在组织、兴趣、隐私是研究方向。产品代码里不出现以它们命名、却只是显式字段或规则的实现，例如 `mood: 'happy'`、`interest_score`。
- **分支：**
  - `main` 是真实生活；
  - `dev:<name>` 只与负责人对话；
  - `fork:<name>` 不能有任何外部互动。

## 3. 不从 V1 带入的词与结构

以下 V1 词汇不作为本仓库的概念或模块名：

- authority / admission / fail-closed / sole writer；
- gate / disposition；
- Character ABI / Harness / Cognition；
- L0 / L1 / L2 / Dream；
- Profile；
- P8 不变式；
- Mem0。

需要类似机制时，在 P 文件里用本仓库自己的话重新定义它要解决的问题。这里限制的是概念与模块的命名，不限制继承 V1 已验证的算法与经验（见 AGENTS“依赖与架构选型”）。

## 4. 怎样增改

- **新的事件种类、新的区分：** 由 Claude 在 P 文件中定义，并在同一个 PR 中写进本文件。
- **Sol 实施中发现需要：** 在 PR 描述中提出，不自行发明写入档案的种类。
- **验收固定包含一项：** 档案中实际出现的 `class/kind` 都已在 §1 登记，且语义一致。
