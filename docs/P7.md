## 1. 目标

**要解决的问题：** 档案记录了它经历了什么、写了什么，却没有记录**每次请求实际把什么放到了模型面前**。

- 一段文字形成之后是否进入过上下文、何时、几次，现在只能按规则推算，无法核对。V1 的“生成了却没有消费者”在 V2 中同样无法被发现。
- 模型上下文由三处代码分别拼出：
  - 对话第 0 步：`context.ts` 的 `dialogueMessages`；
  - 整理请求：`context.ts` 的 `consolidationMessages`；
  - 工具循环第 1–3 步：`server.ts` 直接向数组追加 assistant 与 tool 消息。
- 以后的回忆、浮现、重整如果各自再往请求里加内容，就会重演 V1 的拼接层。

**P7 结束时：**

1. **只有一个组装处。** 所有发给模型的 `messages` 都由它产生，包括工具循环的后续步骤。`server.ts` 不再自己构造消息。
2. **每次模型请求之前写一条 `control/presented`。** 它记录这次请求组装了什么：
   - 用途与步骤；
   - 各部分引用了哪些档案事件、各有多少条消息与多少字；
   - 组装规则版本、请求参数、消息摘要。
3. **呈现记录只声称它能证明的事**（§3.3）：“已组装、即将交给请求发送”。是否发出、是否被接收、模型是否使用，都不由它声称。
4. **研究者可以只读地检查：**
   - 每段文字被呈现了几次、何时；
   - 每次请求的清单；
   - 在 §3.4 的条件下，按清单逐字节重建当时的 `messages`，并用摘要核对。
5. **模型请求、SSE、整理、工具循环与 P1–P6 的全部语义不变。** 唯一的可见变化是档案中多出 `control/presented` 事件，以及由此带来的 `seq` 位移。

这不是回忆、浮现、重整或激活的实现，只为它们提供可靠的观察基础（§5）。

## 2. 范围

### 必须完成

1. **统一组装入口**（在 `context.ts` 中，或拆出一个模块；不新建框架或类层次）。
   - 现有三种请求都经过它：整理、对话第 0 步、对话第 1–3 步。
   - 选择与呈现分开：
     - **选择：** 哪些文字、哪段原文窗口、哪批材料，用 P6 已有的有界读取；
     - **呈现：** 把选出的事件按 P4 规则变成 `messages`，是一个纯函数，输入全部显式给出，包括“现在”的时间。
   - 组装结果同时给出 `messages`、请求参数（`tools` 与 `max_tokens`）和呈现清单，三者来自同一次计算。
2. **`control/presented` 事件**（§3.2），在 `docs/TERMS.md` 登记（本 PR 已登记）。
3. **只读诊断命令**（§3.5）：`presented summary`、`presented writings`、`presented show <seq>`，作为 `dist/maintenance.js` 的子命令，并加相应的 npm 脚本。
4. **测试**（进入 `npm test`）：
   - **差分：** 与 P6 实现在同一组档案状态上比较请求、事件、SSE（按 §3.6 处理序号位移）；
   - **清单与请求一致：** 每次假模型收到的请求，都对应恰好一条呈现记录，摘要与内容相符；
   - **重建：** 对测试中产生的每一条呈现记录，`presented show` 都能精确重建；
   - §4 G5 中的异常与恢复场景。
5. **合成档案：** P6 的生成器加一种带呈现记录的形态，供 G6、G7 的百万事件测量使用。性能脚本复用 P6 的，增加 §4 G7 的指标。

### 明确不做

- 不实现 `recall`、浮现、重整、激活，不改变前景文字的选择规则。
- 不改变任何模型请求的内容、请求参数、工具定义、整理说明与触发时机。
- 不改 `events` 表结构、索引与触发器，不新增持久文件、表或数据库（呈现记录就是档案事件）。
- 不新增运行时依赖，不引入追踪、日志或可观测性框架（如 OpenTelemetry），不新增 HTTP 接口。
- 不修改 P6 验收中记录的遗留问题（§6），它们各有去处。
- 不把呈现记录用于任何运行时决定。P7 只写不读，读取它的机制从 WP-E/WP-F 开始。

## 3. 接口与约束

### 3.1 组装入口的约束

- `server.ts` 中不再出现构造 `Message` 的代码。工具循环把这一步的文本、工具调用与工具结果交给组装入口，得到下一步的 `messages` 与清单。
- “现在”的时间在组装时取一次。同一个值既用于本次新生成的呈现文字（第 0 步回合指示与整理说明中的“现在是……”），也写进清单。
- **第 1–3 步不重新呈现基础消息**（2026-10-22 澄清）：
  - 与 P6 相同，第 0 步的全部消息原样继承，包括回合指示中第 0 步的时间，只在后面追加 assistant 与 tool 消息；
  - 基础部分不重新选择、不重新呈现。
- 组装失败（例如档案读取失败）按现有的存储失败处理：致命，不伪装成模型失败。
- 不为“以后可能的记忆机制”预留插件、注册表或通用接口。以后增加的部分（例如浮现）直接在这个组装入口里加一个部分，同时升级规则版本。

### 3.2 `control/presented`

**写入时机：** 每次调用 `streamModel` 之前，在组装完成之后，写一条：

- 对话的每一步（0–3）各一条；
- 每次整理请求一条，包括失败后重试的请求。

写入失败按存储失败处理，与其他事件相同。

**各列：**

| 列 | 取值 |
| --- | --- |
| `class/kind` | `control/presented` |
| `actor` | `system` |
| `reply_to` | 对话请求为当前 `heard` 的 `id`；整理请求为 `null` |
| `content` | 空字符串 |
| `model` | 这次请求使用的模型名（`config.model`） |
| `meta` | 呈现清单，见下 |

**呈现清单（`meta`）：**

| 字段 | 内容 |
| --- | --- |
| `format` | 清单格式版本，P7 为 `1` |
| `rules` | 组装规则版本，P7 为 `"p7"`。以后任何改变选择或呈现文字的变更都要换一个新值 |
| `purpose` | `"dialogue"` 或 `"consolidation"` |
| `step` | 对话步骤 `0`–`3`；整理请求不带 |
| `previous` | 第 1–3 步：上一步呈现记录的 `id` |
| `now` | 本次请求的组装时间（毫秒）。第 1–3 步继承的基础消息中的时间，是沿 `previous` 链找到的第 0 步记录的 `now`（2026-10-22 澄清） |
| `time_zone` | 运行时的 IANA 时区名（呈现文字中的本地时间依赖它）。运行环境给不出可被 `Intl.DateTimeFormat` 接受的名字时（例如 `TZ` 为空串、POSIX 写法），记为 `null`。运行时呈现文字的方式与 P6 相同（按进程时区），不因这个字段而改变，也不因它无效而失败（2026-10-22 第二次澄清） |
| `owner_name` | 呈现所用的负责人称呼 |
| `writing_chars` | 文字预算（`YUVI_CONTEXT_WRITING_CHARS` 的值；整理说明中会写出它）（2026-10-22 增加） |
| `node_major` | 运行时 Node 的主版本号，整数（2026-10-22 增加） |
| `request` | `tools`：工具名数组，按发送顺序（整理请求为空数组）；`max_tokens`：整理请求的值 |
| `persona` | `sha256`（UTF-8 原文的十六进制摘要）、`chars` |
| `sections` | 按出现顺序排列的各部分（见下表）；没有内容的部分不列出 |
| `total` | `messages`：消息条数；`chars`：各消息 `content` 长度之和（JavaScript 字符串长度，与 `control/error` 的 `request_chars` 同口径） |
| `messages_sha256` | 实际交给请求的 `JSON.stringify(messages)` 的摘要 |

**各部分（`sections`）：** 每个部分都有 `name`、`messages`（条数）、`chars`。按名称另带以下字段：

| `name` | 引用 | 含义 |
| --- | --- | --- |
| `persona` | — | 人设 |
| `writings` | `first_seq`、`last_seq`、`count` | 本场景中 `first_seq`–`last_seq` 之间的全部非空 `inner/wrote`（“非空”的判定与 P6 的 `writings` 相同） |
| `window` | `first_seq`、`last_seq`、`count` | 本场景中这一范围内的全部对话事件 |
| `material` | `first_seq`、`last_seq`、`count` | 整理材料：这一范围内的全部对话事件 |
| `instruction` | 对话请求另带 `heard`（`id`） | 回合指示或整理说明 |
| `step` | `index`、`assistant_text`、`tool_calls`（`id`、`name`、`arguments`，均为实际放进请求的值）、`results`（每个工具调用一项：`{ "checked": <act/checked 的 id> }`，或 `{ "ignored": <工具名> }`） | 第 1–3 步请求中，前面每一步追加的 assistant 消息与 tool 消息；每一步一项 |

**约束：**

- 文字、窗口、材料在 P4/P6 规则下都是连续的一段，用范围加条数即可精确表示。以后出现不连续的部分（例如浮现）时，再用 `seqs` 列表。
- 第 1–3 步清单中的基础部分（`persona`、`writings`、`window`、`instruction`）与第 0 步记录中的相同（2026-10-22 澄清）。
- 清单的大小不随档案增长。默认配置下，对话第 0 步的清单不超过 1,500 字节（包括 2026-10-22 增加的两个字段）；`step` 部分逐字记录模型输出的文本与工具参数，大小随它们变化，如实报告。
- `meta` 中不出现顶层 `usage` 字段（`/api/usage` 以此识别用量），也不出现密钥、基地址或请求头。
- 呈现记录本身不进入任何模型上下文、`check` 结果、文字预算、原文窗口或网页。

### 3.3 能证明什么，不能证明什么

| 状态 | 证据 | 呈现记录是否声称 |
| --- | --- | --- |
| 已组装，即将交给请求发送 | `control/presented` 存在 | **是**，仅此一项 |
| 请求已发出 | 没有直接证据（进程可能在写入后、发送前中断；连接可能失败） | 否 |
| 模型服务已接收并开始响应 | 同一回合随后出现 `reply_attempt`、`act/checked`、下一步的呈现记录、`said`/`silent`，或带 `http_status` 的 `control/error`；整理请求随后出现 `meta.material` 相同的 `inner/wrote` | 否；可以从这些事件推出 |
| 请求完成 | 下一步的呈现记录、`said`/`silent`；整理请求的 `inner/wrote` | 否；可以推出 |
| 失败或结果未知 | 回合以 `control/error` 结束（没有 `http_status` 时，服务是否收到未知）；整理请求后没有对应的 `inner/wrote`（失败或进程中断，无法区分，P4 不记录整理失败） | 否；诊断按下列规则标为 `failed` 或 `incomplete` |
| 模型读了、注意到、采纳或使用了其中某部分 | 档案无法证明 | **永远不声称** |

诊断命令的结局按以下规则推导，并在输出中注明：

- **对话第 k 步：**
  - 有第 k+1 步的呈现记录 → 完成；
  - 否则看回合结局：`said`/`silent` → 完成；`error` → 失败（附 `outcome` 与 `http_status`，如有）；没有结局（只会在中断恢复之前出现）→ 未知。
  - **回合结局与发送结果分开给出**（2026-10-22 澄清）：
    - `status`：`completed` / `failed` / `unknown`；
    - 失败时，`reason`、`outcome`、`http_status` 原样取自该回合 `control/error` 的 `meta`，不固定赋值。例如中断恢复后为 `reason=interrupted`，`outcome` 为记录中的 `unknown` 或 `not_sent`。
- **整理请求：** 下一条整理呈现记录之前，出现 `meta.material` 与清单 `material` 范围相同的 `inner/wrote` → 完成（`completed`）；否则 → 未完成（`incomplete`）。

### 3.4 重建

**能精确重建**：同时满足以下条件时（条件 0 为 2026-10-22 第二次澄清所加），`presented show` 按清单读取档案中的事件，用相同规则重新呈现，所得 `JSON.stringify(messages)` 的 SHA-256 与 `messages_sha256` 相同。

0. 请求所需的原文在档案中无损保存。Node 22 的 SQLite 在写入 TEXT 时把孤立的 UTF-16 代理项替换为 U+FFFD，此后档案中的字节与真实的 U+FFFD 无法区分；回合指示使用的是内存中的原文（P6 行为），因此这类请求不能从档案精确重建；
1. 清单的 `rules` 是当前程序认识的版本；
2. 提供的人设文件摘要与 `persona.sha256` 相同；
3. 当前 Node 主版本等于清单的 `node_major`。Node 22 的 SQLite 读回 TEXT 时在 NUL 处截断，见 §6；不相等时报告 `node_mismatch`，不作精确判断；
4. 时区数据把同一个 `now` 呈现为同样的本地时间。命令使用清单中的 `time_zone`；它为 `null` 时报告 `time_zone_unrecorded`；
5. 第 1–3 步的基础部分按第 0 步记录（沿 `previous` 链）的 `now` 重建；整理说明中的预算取自清单的 `writing_chars`（2026-10-22 澄清）。

**不能重建的，如实报告原因，不猜：**

| 情况 | `show` 的输出 |
| --- | --- |
| 人设文件不同或未提供 | `persona_mismatch`；仍输出其余部分 |
| 规则版本未知（以后的旧记录或新记录） | `rules_unsupported` |
| Node 主版本与 `node_major` 不同（2026-10-22 增加） | `node_mismatch`；仍输出其余部分 |
| 当前 `heard` 在档案中的文本含 U+FFFD，且重建摘要不符（2026-10-22 第二次澄清） | `source_lossy`：可能是写入时的源数据损失，证据强度见下文 |
| `time_zone` 为 `null`（2026-10-22 第二次澄清） | `time_zone_unrecorded`；仍输出其余部分 |
| 其余情况下重建摘要不符 | `mismatch`（这是缺陷，应当报告） |
| P7 之前的请求 | 没有呈现记录，无法重建 |

**三类结果的区分**（2026-10-22 第二次澄清）：

- **前提不满足**（`persona_mismatch`、`node_mismatch`、`rules_unsupported`、`time_zone_unrecorded`）：环境、配置或规则与当时不同，换回相同条件即可重建；
- **可能是历史数据本身不能重建**（`source_lossy`）。这是基于两个条件的推测，不是证明：
  - 依据只有两点：摘要不符，且当前 `heard` 在档案中的文本含 U+FFFD。
  - 它**不证明**原始输入含孤立代理项：档案中的 U+FFFD 也可能本来就是真实输入。
  - 它**不排除**同一条记录同时存在别的重建缺陷：只要满足这两个条件，诊断就报告 `source_lossy`，不再区分。
  - 因此：
    - `source_lossy` 不能作为“实现无缺陷”的证据；
    - 真实的 U+FFFD 输入必须精确重建，不会落入这一类；
    - 判断实现是否正确，以原文无损的请求为准：它们必须为 `exact`，否则为 `mismatch`（G4 ⑤⑥）；
- **实现缺陷**（`mismatch`）：前提都满足、源数据无损，摘要仍不符。

请求体中 `messages` 之外的部分，由 `model`、`request.tools`、`request.max_tokens` 和对应规则版本的代码常量决定。工具描述等常量不逐条写进清单。

### 3.5 只读诊断命令

```
npm run presented -- summary
npm run presented -- writings
npm run presented -- show <seq> [--messages]
```

- **只读：** 以只读方式打开 `archive.sqlite`，不取得服务锁，服务运行时也可执行。输出为 JSON，打印到标准输出。“只读”指逻辑只读（2026-10-22 第二次澄清）：
  - 不写入任何档案事件，不修改主库与 WAL 中已提交的内容；
  - 不打开、不取得、不修改 `service.lock`；
  - 不影响运行中的服务，读到的是一个一致的已提交快照；
  - **允许** SQLite 自身维护 WAL/SHM 协调文件：在已关闭的数据目录上可能创建空的 `archive.sqlite-wal`、`archive.sqlite-shm`；读者会在 `-shm` 中登记读标记。这是 SQLite WAL 模式的正常行为，P3 的启动完整性检查同样如此；不为避免它引入复制、自制 VFS 或额外锁。
- **`summary`：**
  - 呈现记录总数，按用途、步骤和 §3.3 的结局分类；
  - 第一条与最后一条的时间；
  - 呈现记录占用的 `meta` 字节数（总数、平均、最大）。
- **`writings`：** 本场景每条非空 `inner/wrote` 一行：
  - `seq`、写下的时间；
  - 被对话请求呈现的次数、被整理请求呈现的次数，以及其中结局为完成的次数；
  - 第一次与最后一次被呈现的时间；
  - 末尾汇总：从未被呈现的条数。

  次数按请求计（同一回合的第 0–3 步各算一次），输出中注明。
- **`show <seq>`：**
  - 该条呈现记录的清单、§3.3 推导出的结局、§3.4 的重建状态与重建摘要；
  - 加 `--messages` 时另输出重建的 `messages`；
  - 人设文件取自 `YUVI_PERSONA_FILE`。
- **错误输出**遵守 P3 维护命令的约定：只输出固定的诊断文字，不输出文件系统或异常原文。

### 3.6 序号位移与等价

呈现记录占用 `seq`，因此 P7 档案中其他事件的 `seq` 会与 P6 不同。等价按以下方式定义：

- 把 P7 档案中的 `control/presented` 去掉，其余事件按顺序与 P6 档案一一对应，得到 `seq` 映射与 `id` 映射。
- 映射后，P6 与 P7 的事件逐字段相等，忽略 `t_recorded`。凡是引用 `seq` 或 `id` 的字段都先映射：
  - `meta.material.from_seq`、`meta.material.through_seq`；
  - `meta.result_seqs`；
  - `meta.attempt`；
  - `reply_to`；
  - `control/restored` 的 `meta.through_seq`、`meta.through_id`。
- 发给模型的每个请求体（`model`、`messages`、`tools`、`max_tokens`、`stream`、`stream_options`），在相同“现在”下逐字节相等。
- SSE 帧序列相同，帧中的 `id` 按映射替换。
- `/api/usage` 的结果相同。

### 3.7 边界

- 遵守 P1–P6 的全部边界、`AGENTS.md` 的不变量与“依赖与架构选型”。
- 不新增运行时依赖。摘要用 `node:crypto`。Node 要求保持 `>=22.13.0`。
- 不修改 `AGENTS.md`、`docs/ROADMAP.md`、`docs/TERMS.md`、`docs/P1.md`–`docs/P7.md`。
- P6 的增量状态不因呈现记录而改变：它不是对话事件、不是文字、不结束回合、不推进覆盖水位。

### 3.8 由 Sol 决定

- 组装入口的函数划分与命名；是否拆出新模块；
- `previous` 的传递方式；
- 诊断命令的内部实现（例如一次遍历加差分计数）；
- 生成器中呈现记录的比例。比例应接近真实：每个对话回合至少一条，并有工具步骤与整理请求。
