# P6 实施说明

采用 SQLite 与数字增量状态的混合方案，运行时代码仅改 `archive.ts`、`context.ts`、`server.ts`。SQLite 是唯一事实来源；启动完整性检查后重建对话 seq、非空文字 seq/JS 长度、覆盖水位、未结束 heard 及最后对话时间，此后只由成功的 `Archive.append` 更新。正文不缓存，所选事件按主键分批读取；窗口跳跃、整条文字预算、覆盖水位取最大值及积压处理沿用 P4。

`check` 用 `instr`、时间闭区间和场景/分支条件计数，再倒序选至多 40 条，按原来的 JS 字数预算截取并恢复顺序。查询计划为主键选取及必要的顺序扫描，不新增索引。孤立 UTF-16 代理项不能无损绑定 UTF-8，因此仅这种查询使用连接内 SQLite 函数执行原有 `includes`。Node 22 的 SQLite TEXT 在 NUL 处截断，与较新 Node 不同；已探测并保留运行版本的 P4 解码语义，没有借本次改写修复历史行为。

## 实测（Linux / Node 22.23.3，离线假模型）

完整离线 `npm test`：66 通过、0 失败、0 跳过，81.56 秒。差分包含随机档案与真实旧版 `190a272` 服务；新 UUID 按事件顺序建立对应，递归规范化事件、`reply_to`、`meta.attempt`、SSE ID，固定时钟后完整比较请求、事件与 SSE。旧版数据/快照及 schema 不变。测试中取消 P3 维护命令重复编译，避免并行服务读取编译中的产物，维护入口仍实际执行。

F1–F8 均有实测证据：百万档案的正常重启、回复中 SIGKILL、快照恢复首请求等价、整理中 SIGKILL 后原起点续接全部通过。原始计时、计数、查询计划及恢复断言见 [P6-results.json](P6-results.json)；复现命令见 README 的 P6 部分。

无规格偏离，无新增运行时依赖、schema、持久状态、事件或配置。已知边界：启动仍需线性重建；check 总数仍需扫描，罕见代理项查询更慢；`/api/events`、`/api/usage`、P3 检查/快照路径保持原状。RSS 指服务主进程，不包含原有快照子进程。没有对这些范围外路径声称恒定耗时，也未调用真实模型或接触 V1 数据。
