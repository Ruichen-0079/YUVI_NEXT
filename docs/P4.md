## 1. 目标

**要解决的问题：**

- **更早的经历对它来说就此消失。** 到 C1 为止，模型只看到最近 `YUVI_CONTEXT_EVENTS`（默认 200）个对话事件。更早的经历仍在档案里，但它既没有带走任何东西，也没有办法回头查。
- **前缀缓存基本无法命中。** 窗口每回合滑动一格，超过上限以后，每次请求的前缀都会变化。
- **档案的封装形式进入了它的表达。** C1 的上下文把档案字段（事件 id、`seq`、`reply_to`、毫秒时间戳）直接写进对话消息，连它自己说过的话前面也带着这些前缀。真实 DeepSeek 测试中，模型把这些格式模仿进了对外回复。

**P4 结束时：**

1. **经历离开视野之前，先经过它自己。**
   - 程序保证：任何对话事件在离开上下文之前，都已经在一次**整理**中交给它读过。
   - 唯一的例外：整理持续失败、积压超过上限时，事件可以不经整理离开，但这件事本身会入档（§2.2）。
   - 读完以后写什么、写不写，由它决定。程序不摘要、不抽取、不打分。
2. **它写下的东西跟着它。** 整理时写下的文字作为 `inner/wrote` 入档。之后的对话上下文按字数预算放入它最近写下的文字，每条完整放入，不截断。
3. **它能回头查原文。**
   - 对话中可以调用 `check` 查阅档案原文（逐字，带时间与作者）。查阅本身是一个被记录的行为。
   - 能保证与不能保证的事见下文“查得到，不等于被纠正”。
4. **上下文像经历，不像数据库。**
   - 时间是带日期的本地时间，人物用名字或“你”称呼，先后由排列体现。
   - 它自己的话只包含它说过的话。
   - 程序生成的呈现文字中，不出现档案的 id、序号与字段名；原文逐字保留（§2.6）。
5. **窗口稳定，程序加入的内容有界。**
   - 原文窗口的起点很少移动，相邻回合的请求共享前缀。
   - 程序放进请求的各部分，在条数和字数上有界。它写得多，不会让对话失去运行能力。
   - 整个请求能否放进模型的上下文，P4 不作保证。超限时如实失败、可以诊断，不靠裁剪掩盖（§3.1）。

**这不是记忆的实现。**

- 它写下的文字，是它“说得出的那一部分”留给自己的痕迹，是记忆的**一个候选载体**（TERMS §2），不是记忆的定义。
- P4 交付的是条件：让这种痕迹能够形成、能被带走、能被核对。
- 它是否构成“它自己的过去”，留给使用与实验回答（§5）。

**查得到，不等于被纠正。**

P4 对一次更正（例如负责人说“更正：我的猫叫年糕”）**能保证**的只有以下几点：

1. 更正逐字入档，带时间与作者；
2. 它留在原文窗口期间，出现在每一次对话请求中；
3. 它离开窗口之前，至少在一次整理中交给它读过（§2.2 的例外会入档）；
4. 此后，只要 `check` 的条件与它匹配，它会与更早的说法一起，按时间顺序返回。

P4 **不保证**以下几点，它们是要观察的现象，不是要修复的缺陷：

- 它会去查；
- 它会相信或采用更正；
- 它写下的文字会随之改变；
- 旧文字不再重复旧的说法。

程序也不替它判断“哪一条是对的”。

## 2. 范围

### 必须完成

1. **整理。**
   - **是什么：** 一次不面向任何人的模型调用。输入依次为：
     - 人设；
     - 它近期写下的文字（与对话上下文中的相同，见第 3 项）；
     - **材料**；
     - §3.3 的固定说明。
   - **材料：**
     - 本场景中尚未整理过的对话事件（`heard` / `said` / `silent`），按 `seq` 顺序排列；
     - 每条按 §2.6 呈现，作为记录行，不以 `user` / `assistant` 交替的对话形式呈现；
     - 不包括尚未结束的回合的 `heard`，以及它之后的事件；
     - 一次最多 N 个（N = `YUVI_CONTEXT_EVENTS`）。更多时按时间顺序分批，每批一次整理。
   - **请求：**
     - 不提供任何工具，也不要求任何输出格式；
     - 设置 `max_tokens` = `YUVI_CONSOLIDATION_MAX_TOKENS`；
     - 与对话请求一样，设置 `stream_options.include_usage=true`。
   - **结果：**
     - **流正常结束：** 写入恰好一条 `inner/wrote`（§3.2）。
       - `content` 为模型输出的全部文字，原样保存，可以为空；
       - 提供方给出的 `finish_reason` 原样记入 `meta.finish_reason`。因长度上限停止（`"length"`）时，文字照样保存，不补、不删。
     - **失败、超时或进程中断：** **不写任何事件**，这批材料仍算未整理。
       - 标准错误只输出不含密钥的固定信息；收到非 2xx 响应时，附上 HTTP 状态码；
       - 之后重试，同一批材料两次尝试之间间隔不少于 30 秒，具体退避方式由 Sol 决定。
   - **时机：**
     - **空闲：** 同时满足三个条件：距本场景最近一个对话事件已满 `YUVI_CONSOLIDATION_IDLE_MS`；有未整理的材料；没有进行中或排队的回合。
     - **窗口压力：** 原文窗口因为有未整理的事件而无法前进，导致事件数将超过 N（第 2 项）。
       - 此时在下一次对话模型请求之前整理；
       - 处于失败退避期间时不等待，回合照常进行。
     - 整理与对话回合共用串行队列，两者的模型调用不并发。整理进行中到达的消息，照常入档并排队。
     - 启动后按档案状态重新计算，不依赖进程内状态。
2. **原文窗口。** 对话请求中的原文段（`heard` / `said` / `silent`）满足以下几点，具体规则由 Sol 决定：
   - **连续：** 原文段是本场景对话事件按 `seq` 的一个连续后缀，包含当前的 `heard`。
   - **不丢：** 每个未整理的对话事件都在原文段中。
   - **上限：** 事件数不超过 max(N, 未整理的对话事件数)。
   - **积压上限：**
     - 已结束但未整理的对话事件超过 2N 时，在下一次对话模型请求之前，把其中最早的 N 个当作一批，不经整理移出，并写一条 `control/unconsolidated`（§3.2）记录这一批的范围。
     - 这些事件仍在档案中，`check` 仍能查到。
     - 这是唯一允许未经整理就离开原文段的途径。
   - **稳定：** 起点只向前移动。没有整理失败时，两次移动之间至少新增 ⌈N/2⌉ 个对话事件。
   - **确定：** 起点只由档案内容决定，重启不改变它。
3. **它写下的文字进入上下文。**
   - **选择：** 每次对话请求和整理请求，都包含本场景中它写下的非空 `inner/wrote`。从最新一条往前，**整条**放入，直到再放一条就会超过 `YUVI_CONTEXT_WRITING_CHARS` 为止；最新的一条无论长短总是放入。
   - **字数：** 按 JavaScript 字符串长度计，只计文字本身，不计呈现时附加的时间等说明。
   - **呈现：**
     - 按 `seq` 顺序排列，每条附写下的时间；因长度上限停止的，在文字之外注明这一点；
     - 文字本身原样呈现：不截断、不改写、不加其他标注；
     - 不以 `assistant` 角色呈现，因为它们没有对任何人说过；
     - 放在原文段之前，越稳定的内容越靠前。
   - 没有放入的文字不会消失，`check` 仍能查到。
4. **`check`。**
   - **调用流程：** 对话请求提供 `check` 工具（§3.4）。模型调用它时，程序按条件查询档案，把结果作为工具结果返回，再次请求模型；回复继续流式推送。
   - **返回内容：**
     - 范围为本分支、本场景的 `heard`、`said`、`silent` 和非空 `inner/wrote`；
     - 不返回 `reply_attempt`。是否返回其他种类由 Sol 决定，但返回的每一条都必须能辨认是什么：谁说的、它说的、它没有回复，还是它写下的文字；
     - 原文逐字返回，按 §2.6 呈现，带本地时间与作者。
   - **匹配：** 只按可核验的条件匹配，即子串和时间范围。不用嵌入，不让模型判断相关性，不按“重要性”排序。
   - **条数与字数上限：** 都由 Sol 决定，写进 `docs/notes/P4.md`。条数上限不少于 20。
     - 从最近的匹配往前**整条**取，直到再取一条就会超过任一上限为止；
     - 最近的一条匹配总是返回，不论长短；
     - 按时间顺序呈现，并告知匹配总数与返回条数；
     - 不截断任何一条。
   - **记录：**
     - 每次调用写入一条 `act/checked`（§3.2）。
     - 参数无效时不查询，用工具结果告知模型。这条 `act/checked` 带 `meta.invalid=true` 和 `meta.result_seqs=[]`，不得记成一次成功的查询。
5. **一个回合内的多步。**
   - 每个回合最多 4 次模型请求：前 3 次提供 `stay_silent` 和 `check`，第 4 次只提供 `stay_silent`。
   - 回合结局沿用 P2 的表，其中“有文本”指整个回合中**任何一步**有文本：
     - **有文本：** 以 `said` 结束，`content` 为各步文本按顺序直接拼接。`reply_attempt` 仍在第一个增量推出之前写入，一个回合只写一次。
     - **全回合无文本，且最后一步只调用了 `stay_silent`：** 以 `silent` 结束。
     - **全回合无文本的其他情况**（失败、中断、无效的工具输出、第 4 次仍调用 `check`）：与 P1/P2 相同，写 `control/error`。
     - **有文本时：** 最后一步未执行的工具调用（包括第 4 次的 `check`），按 P2 记入 `said.meta.ignored_tools`；失败与中断仍按 P1/P2 记为 `partial` / `unknown`。
   - 同一步里同时调用了 `check` 和 `stay_silent`：执行 `check` 并继续下一步，这个 `stay_silent` 不作为结局。
   - **与 P2 的有意差异：**
     - P2 中，有文本的一步调用的工具一律忽略；现在其中的 `check` 会被执行，回合继续；
     - 有文本时调用 `stay_silent`，仍按 P2 记入 `said.meta.ignored_tools`。
   - **启动恢复不变：** 有 `act/checked`、没有终结事件的 `heard`，按是否有 `reply_attempt` 补记 `not_sent` / `unknown`。
6. **上下文的呈现。** 适用于所有发给模型的消息：对话请求、多步中的工具结果和整理请求。排版与措辞由 Sol 决定，但必须满足：
   - **它自己的话只包含它说过的话。**
     - `assistant` 消息的 `content` 只能是它说过的话：过去回合中 `said` 的 `content` 原文，或当前回合前几步已推出的文本。
     - 前后不加任何东西：时间、名字、说明都不加。
   - **区分原文与呈现文字。** 消息中的文字分为两类：
     - **原文：** 人设、负责人的消息、它说过的话、它写下的文字。无论其中出现什么词，包括技术词汇、`键=值`、JSON，都**逐字保留**，不改写、不转义、不删减。
     - **呈现文字：** 原文之外、由程序生成的一切。例如时间、称呼、标签、沉默的说明、回合指示、工具结果的排版、整理说明。
     - 呈现文字引用原文时（例如回合指示引用当前那句话），整段逐字引用，不摘取片段。
   - **呈现文字里没有档案字段。** 以下内容不出现在**呈现文字**中：
     - 事件 id；
     - `seq` 及其数值标注；
     - 毫秒时间戳；
     - 字段名或事件种类名，例如 `reply_to`、`actor`、`t_recorded`、`meta`、`heard`、`said`、`silent`、`inner`、`owner`、`yuvi`；
     - `键=值` 或 JSON 形式的记录。

     这条规则只约束程序生成的封装，不约束原文。工具调用本身（`tools` 定义与 `tool_calls` 参数）属于协议结构，也不在此限。
   - **时间可读。**
     - 原文、它写下的文字、`check` 结果中的时间，都用主机本地时区（`TZ`）下带日期的可读时间，例如 `2026-10-21 14:03`，并注明或可推知时区；
     - 回合指示与整理说明附上当前的本地时间；
     - 当前时间不得放在原文段之前，否则会破坏前缀稳定。
   - **人物用称呼。**
     - 负责人用 `YUVI_OWNER_NAME` 称呼；
     - YUVI 自己用“你”称呼，或由消息角色体现；
     - 不出现 `owner`、`yuvi`、`system` 这类档案取值。
   - **关系用排列与自然语言表达。**
     - 先后由排列体现；“当前回应的是哪一句”由回合指示用时间和原文引用表达；
     - 沉默用一句中性的话表达它没有回复，并且不能写在 `assistant` 消息里；
     - 不相邻的回复关系（例如排队时，对“甲”的回复出现在“乙”之后），可以用 `user` 角色的一句自然语言说明，或不加说明。
   - **只在输入端解决。** 程序不对模型的输出做任何过滤、替换或改写。
7. **用量。**
   - 每次模型调用（包括整理，以及回合中的每一步）的 `usage`，原样记录**恰好一次**，记在该调用产生的事件上：
     - 整理：记在 `inner/wrote`；
     - 调用了 `check` 的一步：记在这一步产生的某条 `act/checked`；
     - 最后一步：记在终结事件。
   - 失败的整理没有事件，它的用量不记录（§5）。
   - `/api/usage`：
     - token 和其他数值字段的合计，覆盖所有带 `meta.usage` 的事件；
     - `turns` 与 `turns_with_usage` 保持 P2 的含义，只计 `said` / `silent` / `error`。
8. **网页。** 不显示 `inner/wrote`、`act/checked` 和 `control/unconsolidated`；对话部分的显示不变。
9. **登记事件种类。** `inner/wrote`、`act/checked`、`control/unconsolidated` 已由本 PR 在 `docs/TERMS.md` 登记，实现必须与登记的含义一致。
10. **测试与说明。**
    - `npm test` 覆盖上述行为，不访问外部网络和真实模型。
    - `README.md` 写明：
      - 新增的配置；
      - 整理的时机与积压上限；
      - `check`，以及“查得到 ≠ 被纠正”；
      - 它写下的文字保存在档案中，页面不显示，负责人可以通过 `/api/events` 或档案读取。
    - `docs/notes/P4.md` 写明实现选择，不超过一页。

### 明确不做

- **`recall`。** P4 不实现。“什么会自己想起来”是开放问题，用关键词检索它自己写的文字，不应冒充回忆（§5）。
- **其他写作与私人内容：** 对话中随时写内心记录的 `write` 工具；私人场景 `self:private`；有记录的审阅程序。
- **对它的文字的处理：**
  - 改写、取代、淡去或删除它的文字的任何机制；
  - 给文字加分类、标题、标签或重要性；
  - 截断、压缩或代写摘要。
- **纠正的程序化：** 程序判断哪个说法有效；更正的取代关系；把更正自动放进上下文。
- **其他记忆相关结构：** 章节、自我描述的修改、心意。
- **程序侧的理解或检索设施：** 摘要、事实抽取、嵌入、向量索引或全文索引。
- **输出处理：** 对回复做任何后处理或过滤。
- **单条超长输入：** 不处理单条超长消息的感知问题。这是 C1 起就有的边界，见 §5。
- **档案结构：** 不改 `events` 表的结构、触发器或索引，不新增表。
- **其他周期的工作：** 主动开口（C3）、V1 导入（P5）、潜在组织、多场景、预算上限与金额。
- **既有语义：** 不改变 P1–P3 事件的含义；§2.5 所列的有意差异除外。

## 3. 接口与约束

### 3.1 配置

| 变量                            | 默认      | 含义                                                       |
| ------------------------------- | --------- | ---------------------------------------------------------- |
| `YUVI_CONTEXT_EVENTS`           | `200`     | 不变。即 N：原文窗口的事件数上限，也是一次整理的材料数上限 |
| `YUVI_CONTEXT_WRITING_CHARS`    | `16000`   | 上下文中它写下的文字的字数预算（§2.3）                     |
| `YUVI_CONSOLIDATION_MAX_TOKENS` | `4000`    | 一次整理的输出上限（`max_tokens`）                         |
| `YUVI_CONSOLIDATION_IDLE_MS`    | `3600000` | 本场景空闲多久以后整理（毫秒）                             |
| `YUVI_OWNER_NAME`               | `负责人`  | 给模型的文字中对负责人的称呼                               |

**取值规则：**

- 三个数值变量为 1–2147483647 的整数；
- `YUVI_OWNER_NAME` 为非空白文本；
- 无效值的错误信息指出变量名，不输出值。

**容量：P4 保证什么。** 程序放进请求的部分，有以下上界。

| 部分             | 上界                                                                                  |
| ---------------- | ------------------------------------------------------------------------------------- |
| 原文段           | 不超过 max(N, 未整理事件数) 个事件；积压上限使其不超过 2N 个已结束事件，加上尚未结束的回合的 `heard`                         |
| 它写下的文字     | 合计不超过 `YUVI_CONTEXT_WRITING_CHARS`；唯一例外是最新一条，其长度受 `YUVI_CONSOLIDATION_MAX_TOKENS` 限制 |
| 整理材料         | 不超过 N 个事件                                                                       |
| `check` 结果     | 不超过 Sol 设定的条数与字数上限；唯一例外是最近的一条匹配                             |
| 一个回合的请求数 | 不超过 4 次                                                                           |

**P4 不保证什么。**

- **不保证整个请求放得进模型的上下文。** 程序不计 token。单条消息、人设、它的回复、单条匹配结果的长度都不受限制，上表的上界是按事件计或按字计的，不是按 token 计的。
- 默认值的量级（推断）：200 个普通长度的对话事件、16000 字文字、一条约 4000 token 的最新文字，加上人设，在常见的 128k 上下文中有余量。

**超限时的表现。** 不裁剪后重发，不伪造事件。

- **对话请求**（包括多步中的后续请求）被拒或失败：
  - 按 P1/P2 写 `control/error`（`not_sent` 或 `partial`），同一回合不重试；
  - 这条 `control/error`（`meta.reason="model_failure"`）附两个诊断字段（启动恢复补记的 `interrupted` 不带）：
    - `meta.request_chars`：失败的那次请求中，所有消息 `content` 的 JavaScript 字符串长度之和；
    - `meta.http_status`：收到非 2xx 响应时，记录其状态码。
  - 两者都不含提供方的响应体。
- **整理请求**被拒或失败：按 §2.1，不写事件，退避重试，标准错误附状态码。持续失败时，由积压上限让对话继续（§2.2）。
- **一条读不下的消息：**
  - 在它离开原文段之前，之后的回合都会以 `control/error` 结束。
  - 它最终会经积压上限离开，这期间每个回合都有记录。在默认 N 下，这可能需要很多回合。
  - 负责人可以临时调小 `YUVI_CONTEXT_EVENTS`，让它更早离开。这一点是推断，未实测。
  - P4 不解决“读不下”本身（§5）。

### 3.2 事件

| 事件                     | 字段                                                                                                                                                                                                                                                                                        |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `inner/wrote`            | `actor="yuvi"`；`scene` 为材料所在场景（P4 中为 `"web"`）；`reply_to=null`；`model` 必填；`content` 为模型输出全文，可为空。`meta.material = { from_seq, through_seq }`：本批材料中第一个和最后一个对话事件的 `seq`。提供方给出时带 `meta.finish_reason`；有用量时带 `meta.usage`               |
| `act/checked`            | `actor="yuvi"`；`scene="web"`；`reply_to` 为当前回合的 `heard`；`model` 必填；`content=""`。`meta.arguments` 为模型给出的参数（解析后的对象）；`meta.result_seqs` 为返回给模型的事件的 `seq`，按呈现顺序；`meta.total` 为匹配总数；参数无效时 `meta.invalid=true`。有用量时带 `meta.usage` |
| `control/unconsolidated` | `actor="system"`；`scene="web"`；`reply_to=null`；`content=""`。`meta.material = { from_seq, through_seq }`：这一批未经整理就移出原文段的对话事件中，第一个和最后一个的 `seq`；`meta.reason="backlog"`                                                                                       |

**“已整理到”C：** 本场景所有 `inner/wrote` 与 `control/unconsolidated` 的 `meta.material.through_seq` 中的最大值；都没有时为 0。

**材料范围：** 两种事件的材料范围合在一起，前后相接、不重叠。

### 3.3 整理说明（固定文本）

整理请求的最后一条消息（`user` 角色）为下面的文字，前面附当前的本地时间。

- `{owner}` 替换为 `YUVI_OWNER_NAME`，`{chars}` 替换为 `YUVI_CONTEXT_WRITING_CHARS`。
- Sol 可以调整空行，不改措辞。需要改措辞时提出，由 Claude 修改本文件。

> 这不是一次对话，不需要回复任何人。
>
> 上面是你最近的一段经历，按档案原样列出；如果你以前写下过什么，也在上面。
>
> 你可以写下任何想留给以后的自己的东西，也可以什么都不写。写什么、写多少、用什么形式，都由你决定；不需要完整，也不需要准确。

### 3.4 工具

```ts
check({ query?: string, from?: string, to?: string })
```

- **`query`：** 子串匹配。是否忽略大小写、是否按空白拆成多个词，由 Sol 决定，写进 `docs/notes/P4.md`。
- **`from` / `to`：** ISO 8601 日期或日期时间，包含端点；没有时区时按本地时区。
- **三者都缺省：** 返回最近的若干条。
- Sol 可以增加可选参数，但不改变这三个参数的含义。
- **工具描述（固定）：** “查阅档案原文：返回本场景中符合条件的原始记录，逐字，带时间和作者，也包括你自己以前写下的文字。查阅会被记录。当你要把过去的事当作事实告诉别人时，先用它核对。”
- `stay_silent` 与 P2 相同。

### 3.5 边界

- 遵守 P1 §3.6、P2 §3、P3 §3 的全部边界，以及 `AGENTS.md` 的不变量。
- **程序不解释它写下的文字：**
  - 不解析、不分类、不截断；
  - 不根据其内容改变行为；
  - 只做三件事：按字数整条选入并原样放进上下文；`check` 的子串匹配；记录提供方给出的 `finish_reason`。
- **程序不处理模型的输出：** 不过滤、不替换、不改写（§2.6）。
- **档案结构不变：**
  - 不修改 `events` 表的结构、触发器与索引，不新增表；
  - 因此，P3 创建的数据目录与快照不经迁移即可使用，旧快照也能通过 `verify-snapshot`；
  - 它写下的文字就是档案中的事件，自然进入快照与恢复。
- 不修改 `AGENTS.md`、`docs/ROADMAP.md`、`docs/TERMS.md`、`docs/P1.md`–`docs/P4.md`。
- 不新增运行时依赖。Node 版本要求保持 `>=22.13.0`。

  - 是否对模型的输出做过滤或改写；
  - 整理说明与工具描述是否与 §3.3、§3.4 一致。
- **是否存在以下路径：**
  - 事件既未经整理、也没有 `control/unconsolidated` 就离开原文段；
  - 伪造结局，或重复写终结事件；
  - 修改已有档案。
- **测试是否真实覆盖** D3、D6、D7、D9、D11、D19、D20、D21。

**实机检查**（不作为判据）：

- **做法：** 负责人或 Sol 用 DeepSeek，设 `YUVI_CONTEXT_EVENTS=20`、`YUVI_CONSOLIDATION_IDLE_MS=120000`，对话 30 分钟以上，其中包含一次更正。
- **观察：**
  - 对外回复中是否仍出现档案格式（id、序号、时间戳、字段名）；
  - 整理时，它写成的是回复体、摘要体，还是别的样子；文字长度是否随时间增长；
  - 被问到已离开窗口的事时，它是否调用 `check`；
  - 查到更正后，它是否采用了更正；之后整理写下的文字是否随之改变；
  - 窗口稳定期间，`/api/usage` 中的缓存命中是否上升。
- **记录：** 观察记在 PR 中，作为后续 P 的输入，不回溯判定 P4 不通过。

## 5. 有意保持开放的问题

P4 不回答以下问题，也不为它们预设结构：

1. **它写下的文字在多大程度上是“它的记忆”。**
   - 文字只覆盖说得出的那部分；
   - 它们也可能只是在复述档案。
   - 实机检查和日常使用先提供观察，系统比较留给 X16（重建式记忆与完全回忆）。
2. **它怎样理解、采纳和重新解释过去。**
   - 查到更正以后，它是否相信、是否改写自己的文字、旧的说法是否还会在它写下的东西里延续，都是要观察的现象。
   - P4 不加任何“更正优先”的规则。
   - 负责人已确认（ROADMAP §2.2）：更正的采纳是研究观察，P4 不增加任何“更正必然生效”的机制。
   - 身份认证、权限与访问范围等可信边界，由程序确定，不属于它可以重新解释的记忆事实。
3. **什么会自己想起来。**
   - P4 中，它近期的文字按时间与字数整条进入上下文。这是①类暂时替代：按时间选择，不是联想。
   - 更早的文字只能通过 `check` 找到，而那是一个有意的查阅动作。
   - `recall` 等到有了不只是关键词检索的机制，再定义。
4. **改写与淡去。**
   - 旧文字只是因为预算放不下，才离开上下文。
   - 它在整理时能看到并重写自己最近的文字，但无法取代旧条目。
   - 是否需要“取代”关系，看使用情况再定。
5. **告知预算的影响。**
   - 整理说明如实告诉它文字的容量，这可能让它写得更短、更像摘要。
   - 不告诉它也是一种选择，但那等于在它不知情时替它丢弃内容。
   - P4 选择告知；影响是什么，看实机检查。
6. **整理的时机。** 由程序按空闲与窗口压力决定，这是①类暂时替代。它能否自己决定什么时候整理、整理多久，留给后续。
7. **积压上限。**
   - 积压时，事件不经整理离开，这是可用性优先的选择：宁可如实记下“没有整理”，也不让对话停止。
   - 是否让它知道这件事，留给后续。
8. **单条超长输入的感知。**
   - 一条长度超过模型上下文的消息，C1 起就会让回合失败。
   - P4 的积压上限只保证它最终离开窗口，不解决“读不下”。
   - 怎样感知长材料，例如分段阅读、作为附件，留给后续。
9. **呈现的残留影响。**
   - P4 去掉了档案字段，但可读时间、称呼与记录行本身仍是一种格式，它仍可能影响表达。
   - 实机检查会观察；能否进一步改善，看结果。
10. **可见与私人。**
    - P4 中，它的文字属于 `web` 场景，页面不显示，负责人可以读档案。整理说明如实告诉它这一点。
    - 私人场景与有记录的审阅程序，留给私人场景方向。
11. **参数。** N 与字数预算的大小（X1）；沉默的理由是否进入它自己的上下文。
12. **失败整理的用量**不入档。如果 C3 的预算需要，再定。
