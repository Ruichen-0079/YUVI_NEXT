# P4　整理与查档：经历离开视野之前，先经过它自己

> 周期 C2 的第一个工作包。实施：Sol。验收：Claude。前置：P3 已合并到 `main`（`e74d2f1`）。
>
> 只需读本文件、[`AGENTS.md`](../AGENTS.md) 与 [`docs/TERMS.md`](TERMS.md)。本文件与其他资料冲突时，以本文件为准。

## 1. 目标

**要解决的问题。** 到 C1 为止，模型只看到最近 `YUVI_CONTEXT_EVENTS`（默认 200）个对话事件。更早的经历仍在档案里，但对它来说就此消失：

- 它没有带走任何东西；
- 它也没有办法回头查。

此外，窗口每回合滑动一格。超过上限以后，每次请求的前缀都会变化，提供方的前缀缓存基本无法命中。

**P4 结束时：**

1. **经历离开视野之前，先经过它自己。** 程序保证：任何对话事件在离开上下文之前，都已经在一次**整理**中交给它读过。读完以后写什么、写不写，由它决定。程序不摘要、不抽取、不打分。
2. **它写下的东西跟着它。** 整理时写下的文字作为 `inner/wrote` 入档，并出现在之后的对话上下文中。
3. **它能回头查原文。** 对话中可以调用 `check`，查阅档案原文（逐字，带时间与作者）。查阅本身是一个被记录的行为。负责人的纠正因此查得到：更早的说法和后来的更正，会按时间顺序一起返回。
4. **它知道时间。** 上下文中的时间是带日期的本地时间。它能知道现在是什么时候，以及一件事发生在哪一天。
5. **窗口稳定。** 原文窗口的起点很少移动，相邻回合的请求共享前缀。

**这不是记忆的实现。**

- 它写下的文字，是它“说得出的那一部分”留给自己的痕迹，是记忆的**一个候选载体**（TERMS §2），不是记忆的定义。
- P4 交付的是条件：让这种痕迹能够形成、能被带走、能被核对。
- 它是否构成“它自己的过去”，留给使用与实验回答（§5）。

## 2. 范围

### 必须完成

1. **整理。**
   - **是什么：** 一次不面向任何人的模型调用。输入依次为：
     - 人设；
     - 它近期写下的文字（与对话上下文中的相同，见第 3 项）；
     - **材料**；
     - §3.3 的固定说明。
   - **材料：**
     - 本场景中尚未整理过的对话事件（`heard` / `said` / `silent`），按 `seq` 顺序排列；
     - 每条带本地时间与作者，作为**记录行**呈现，不以 `user` / `assistant` 交替的对话形式呈现；
     - 不包括尚未结束的回合的 `heard`，以及它之后的事件；
     - 一次最多 N 个（N = `YUVI_CONTEXT_EVENTS`）。更多时按时间顺序分批，每批一次整理。
   - 整理请求**不提供任何工具**，也不要求任何输出格式；与对话请求一样设置 `stream_options.include_usage=true`。
   - **结果：**
     - 流正常结束：写入恰好一条 `inner/wrote`（§3.2）。`content` 为模型输出的全部文字，原样保存，可以为空。
     - 失败、超时或进程中断：**不写任何事件**，这批材料仍算未整理。标准错误只输出不含密钥的固定信息。之后重试，同一批材料两次尝试之间间隔不少于 30 秒，具体退避方式由 Sol 决定。
   - **时机：**
     - **空闲：** 距本场景最近一个对话事件已满 `YUVI_CONSOLIDATION_IDLE_MS`；有未整理的材料；没有进行中或排队的回合。
     - **窗口压力：** 原文窗口因为有未整理的事件而无法前进，导致事件数将超过 N（第 2 项）。此时在下一次对话模型请求之前整理；但处于失败退避期间时，不等待，回合照常进行。
     - 整理与对话回合共用串行队列，两者的模型调用不并发。整理进行中到达的消息，照常入档并排队。
     - 启动后按档案状态重新计算，不依赖进程内状态。
2. **原文窗口。** 对话请求中的原文段（`heard` / `said` / `silent`）满足以下五点，具体规则由 Sol 决定：
   - **连续：** 原文段是本场景对话事件按 `seq` 的一个连续后缀，包含当前的 `heard`；
   - **不丢：** 每个未整理的对话事件都在原文段中；
   - **上限：** 事件数不超过 max(N, 未整理的对话事件数)；
   - **稳定：** 起点只向前移动。没有整理失败时，两次移动之间至少新增 ⌈N/2⌉ 个对话事件；
   - **确定：** 起点只由档案内容决定，重启不改变它。
3. **它写下的文字进入上下文。**
   - 每次对话请求和整理请求，都包含本场景最近的 K 条非空 `inner/wrote`（K = `YUVI_CONTEXT_WRITINGS`），按 `seq` 顺序排列，每条带写下的时间。
   - 原样呈现：不截断、不改写、不加标注。
   - 不以 `assistant` 角色呈现，因为它们没有对任何人说过。
   - 放在原文段之前，越稳定的内容越靠前。
4. **`check`。**
   - **调用流程：** 对话请求提供 `check` 工具（§3.4）。模型调用它时，程序按条件查询档案，把结果作为工具结果返回，再次请求模型；回复继续流式推送。
   - **返回内容：**
     - 范围为本分支、本场景的 `heard`、`said`、`silent` 和非空 `inner/wrote`；
     - 不返回 `reply_attempt`。是否返回其他种类由 Sol 决定，但返回的每一条都必须能辨认种类；
     - 原文逐字返回，带本地时间、作者与 `seq`。
   - **匹配：** 只按可核验的条件匹配，即子串和时间范围。不用嵌入，不让模型判断相关性，不按“重要性”排序。
   - **条数上限：** 由 Sol 决定，不少于 20。匹配超过上限时，返回最近的若干条（按时间顺序呈现），并告知匹配总数。
   - **记录：** 每次调用写入一条 `act/checked`（§3.2）。参数无效时不查询，用工具结果告知模型；这条 `act/checked` 带 `meta.invalid=true`、`meta.result_seqs=[]`，不得记成一次成功的查询。
5. **一个回合内的多步。**
   - 每个回合最多 4 次模型请求：前 3 次提供 `stay_silent` 和 `check`，第 4 次只提供 `stay_silent`。
   - 回合结局沿用 P2 的表，其中“有文本”指整个回合中**任何一步**有文本：
     - **有文本：** 以 `said` 结束，`content` 为各步文本按顺序直接拼接。`reply_attempt` 仍在第一个增量推出之前写入，一个回合只写一次。
     - **全回合无文本，且最后一步只调用了 `stay_silent`：** 以 `silent` 结束。
     - **全回合无文本的其他情况**（失败、中断、无效的工具输出、第 4 次仍调用 `check`）：与 P1/P2 相同，写 `control/error`。
     - 有文本时，最后一步未执行的工具调用（包括第 4 次的 `check`）按 P2 记入 `said.meta.ignored_tools`；失败与中断仍按 P1/P2 记为 `partial` / `unknown`。
   - 同一步里同时调用了 `check` 和 `stay_silent`：执行 `check` 并继续下一步，这个 `stay_silent` 不作为结局。
   - **与 P2 的有意差异：**
     - P2 中，有文本的一步调用的工具一律忽略；现在其中的 `check` 会被执行，回合继续；
     - 有文本时调用 `stay_silent`，仍按 P2 记入 `said.meta.ignored_tools`。
   - **启动恢复不变：** 有 `act/checked`、没有终结事件的 `heard`，按是否有 `reply_attempt` 补记 `not_sent` / `unknown`。
6. **时间。**
   - 原文段、它写下的文字和 `check` 结果中的时间，都是主机本地时区（`TZ`）下带日期的可读时间，例如 `2026-10-21 14:03`，注明或可推知时区。
   - 回合指示与整理说明附上当前的本地时间。
   - 当前时间不得放在原文段之前，否则会破坏前缀稳定。
   - P2 上下文中的毫秒时间戳与 uuid 前缀，保留或去掉由 Sol 决定；每条原文仍须能辨认作者与先后。
7. **用量。**
   - 每次模型调用（包括整理，以及回合中的每一步）的 `usage`，原样记录**恰好一次**，记在该调用产生的事件上：
     - 整理：记在 `inner/wrote`；
     - 调用了 `check` 的一步：记在这一步产生的某条 `act/checked`；
     - 最后一步：记在终结事件。
   - 失败的整理没有事件，它的用量不记录（§5）。
   - `/api/usage`：
     - token 和其他数值字段的合计，覆盖所有带 `meta.usage` 的事件；
     - `turns` 与 `turns_with_usage` 保持 P2 的含义，只计 `said` / `silent` / `error`。
8. **网页。** 不显示 `inner/wrote` 和 `act/checked`；对话部分的显示不变。
9. **登记事件种类。** `inner/wrote`、`act/checked` 已由本 PR 在 `docs/TERMS.md` 登记，实现必须与登记的含义一致。
10. **测试与说明。**
    - `npm test` 覆盖上述行为，不访问外部网络和真实模型。
    - `README.md` 写明：
      - 新增的配置；
      - 整理的时机；
      - `check`；
      - 它写下的文字保存在档案中，页面不显示，负责人可以通过 `/api/events` 或档案读取。
    - `docs/notes/P4.md` 写明实现选择，不超过一页。

### 明确不做

- **`recall`。** P4 不实现。“什么会自己想起来”是开放问题，用关键词检索它自己写的文字，不应冒充回忆（§5）。
- **其他写作与私人内容：** 对话中随时写内心记录的 `write` 工具；私人场景 `self:private`；有记录的审阅程序。
- **对它的文字的处理：**
  - 改写、取代、淡去或删除它的文字的任何机制；
  - 给文字加分类、标题、标签或重要性。
- **其他记忆相关结构：** 章节、自我描述的修改、心意。
- **程序侧的理解或检索设施：** 摘要、事实抽取、嵌入、向量索引或全文索引。
- **档案结构：** 不改 `events` 表的结构、触发器或索引，不新增表。
- **其他周期的工作：** 主动开口（C3）、V1 导入（P5）、潜在组织、多场景、预算上限与金额。
- **既有语义：** 不改变 P1–P3 事件的含义；§2.5 所列的有意差异除外。

## 3. 接口与约束

### 3.1 配置

| 变量                         | 默认      | 含义                                                         |
| ---------------------------- | --------- | ------------------------------------------------------------ |
| `YUVI_CONTEXT_EVENTS`        | `200`     | 不变。即 N：原文窗口的事件数上限，也是一次整理的材料数上限   |
| `YUVI_CONTEXT_WRITINGS`      | `20`      | 即 K：上下文中包含它最近写下的非空文字的条数                 |
| `YUVI_CONSOLIDATION_IDLE_MS` | `3600000` | 本场景空闲多久以后整理（毫秒）                               |

两个新变量为 1–2147483647 的整数。无效值的错误信息指出变量名，不输出值。

### 3.2 事件

| 事件          | 字段                                                                                                                                                                                                                                                               |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `inner/wrote` | `actor="yuvi"`；`scene` 为材料所在场景（P4 中为 `"web"`）；`reply_to=null`；`model` 必填；`content` 为模型输出全文，可为空。`meta.material = { from_seq, through_seq }`：本批材料中第一个和最后一个对话事件的 `seq`。有用量时带 `meta.usage`                        |
| `act/checked` | `actor="yuvi"`；`scene="web"`；`reply_to` 为当前回合的 `heard`；`model` 必填；`content=""`。`meta.arguments` 为模型给出的参数（解析后的对象）；`meta.result_seqs` 为返回给模型的事件的 `seq`，按呈现顺序；`meta.total` 为匹配总数；参数无效时 `meta.invalid=true`。有用量时带 `meta.usage` |

**“已整理到”C：** 本场景所有 `inner/wrote` 的 `meta.material.through_seq` 中的最大值；没有整理过时为 0。

**材料范围：** 各次整理的材料范围前后相接、不重叠。

### 3.3 整理说明（固定文本）

- 整理请求的最后一条消息（`user` 角色）为下面的文字，前面附当前本地时间。
- Sol 可以调整空行，不改措辞。需要改措辞时提出，由 Claude 修改本文件。

> 这不是一次对话，不需要回复任何人。
>
> 上面是你最近的一段经历，按档案原样列出；如果你以前写下过什么，也在上面。
>
> 你可以写下任何想留给以后的自己的东西，也可以什么都不写。写什么、写多少、用什么形式，都由你决定；不需要完整，也不需要准确。
>
> 你写下的文字会原样保存，并出现在你以后的上下文里。它不会出现在对话中，但负责人能够查阅档案。原始记录不会因此改变，以后在对话中需要时，可以用 check 查阅原文。

### 3.4 工具

```ts
check({ query?: string, from?: string, to?: string })
```

- **`query`：** 子串匹配。是否忽略大小写、是否按空白拆成多个词，由 Sol 决定，写进 `docs/notes/P4.md`。
- **`from` / `to`：** ISO 8601 日期或日期时间，包含端点；没有时区时按本地时区。
- **三者都缺省：** 返回最近的若干条。
- Sol 可以增加可选参数，但不改变这三个参数的含义。
- **工具描述（固定）：** “查阅档案原文：返回本场景中符合条件的原始记录，逐字，带时间和作者，也包括你自己以前写下的文字。查阅会被记录。当你要把过去的事当作事实告诉别人时，先用它核对。”
- `stay_silent` 与 P2 相同。

### 3.5 边界

- 遵守 P1 §3.6、P2 §3、P3 §3 的全部边界，以及 `AGENTS.md` 的不变量。
- **程序不解释它写下的文字：**
  - 不解析、不分类、不截断；
  - 不根据其内容改变行为；
  - 唯一的例外是两件事：原样放进上下文，以及 `check` 的子串匹配。
- **档案结构不变：**
  - 不修改 `events` 表的结构、触发器与索引，不新增表；
  - 因此，P3 创建的数据目录与快照不经迁移即可使用，旧快照也能通过 `verify-snapshot`；
  - 它写下的文字就是档案中的事件，自然进入快照与恢复。
- 不修改 `AGENTS.md`、`docs/ROADMAP.md`、`docs/TERMS.md`、`docs/P1.md`–`docs/P4.md`。
- 不新增运行时依赖。Node 版本要求保持 `>=22.13.0`。

### 3.6 由 Sol 决定

- 窗口起点的规则（须满足 §2.2）；
- 原文行、它的文字与工具结果的排版及消息角色（须满足 §2.1、§2.3、§2.6）；
- 回合指示的措辞；
- `check` 的匹配细节与条数上限；
- 退避与调度方式；
- 代码结构。

## 4. 验收标准

**执行方式：**

- 与 P3 相同：Claude 用自己编写的脚本、假模型服务与 SQLite 读取工具，对真实进程和真实命令执行检查。环境为 Linux、Node 22。
- 假模型能够：
  - 认出整理请求（不带 `tools`）；
  - 流式返回 `check` 调用；
  - 记录每一步的请求；
  - 每次调用返回不同的 `usage`。
- **标记：** 由驱动或假模型生成的唯一字符串，用来在请求中定位内容。
- **前缀关系：** 指请求 `messages` 数组在 JSON 层面逐项相等。

## 5. 有意保持开放的问题

P4 不回答以下问题，也不为它们预设结构：

1. **它写下的文字在多大程度上是“它的记忆”。**
   - 文字只覆盖说得出的那部分；
   - 它们也可能只是在复述档案。
   - 实机检查和日常使用先提供观察，系统比较留给 X16（重建式记忆与完全回忆）。
2. **什么会自己想起来。**
   - P4 中，它近期的文字按时间进入上下文。这是①类暂时替代：按时间选择，不是联想。
   - 更早的文字只能通过 `check` 找到，而那是一个有意的查阅动作。
   - `recall` 等到有了不只是关键词检索的机制，再定义。
3. **改写与淡去。**
   - 旧文字只是因为不再属于最近 K 条，才离开上下文。
   - 它在整理时能看到并重写自己最近的文字，但无法取代旧条目。
   - 是否需要“取代”关系，看使用情况再定。
4. **整理的时机。** 由程序按空闲与窗口压力决定，这是①类暂时替代。它能否自己决定什么时候整理、整理多久，留给后续。
5. **可见与私人。**
   - P4 中，它的文字属于 `web` 场景，页面不显示，负责人可以读档案。整理说明如实告诉它这一点。
   - 私人场景与有记录的审阅程序，留给私人场景方向。
6. **参数与比较。** N 与 K 的大小（X1）；沉默的理由是否进入它自己的上下文。
7. **失败整理的用量**不入档。如果 C3 的预算需要，再定。
