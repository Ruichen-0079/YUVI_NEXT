## 1. 目标

### 1.1 退出条件：一项研究结果，而不是一组基础设施

V1 反复陷入“先完成地基，再开展研究”：工程能力一层层完成，记忆是否在经历中起作用却从未被测量（[V1 归档 03 §2.3](history/v1/03-engineering-lessons.md)）。本里程碑的完成判据不是“索引建好了、评测台搭好了”，而是：

> **在一段可复现、跨越 9 周的合成生活中，我们能够衡量 YUVI 对旧经历的查找与呈现：准确知道它找到了什么、漏掉了什么、为什么漏掉，以及这些结果怎样随时间和干扰而变化。**

交付物是一份**基线报告**（§4.8），用数据回答以下六个问题。它们是 WP-E 的出发点；答案可以是负面的。

| # | 问题 | 怎样回答 |
| --- | --- | --- |
| Q1 | 旧信息是否仍可被查到、被呈现？ | 按经历的年龄分组的呈现覆盖率，三个对照臂分开 |
| Q2 | 新近的说法与旧事实如何竞争？ | 同一话题新旧版本的排序位置与是否同时呈现 |
| Q3 | 更正前后的相关材料能否同时找到？ | 含更正的探针中，新旧两个版本都被呈现的比例 |
| Q4 | 话题高频重复是否掩盖罕见的旧事实？ | 同一组探针在“平常”与“高干扰”两段生活中的差异 |
| Q5 | 检索到的与实际呈现的差多少？ | 进入候选、排在前 100、被呈现，三者逐级的差距与原因 |
| Q6 | 失败是否可重现、可解释？ | 每次遗漏都有机械判定的原因类别和一条复现命令；“原因不明”为零 |

### 1.2 三个层次，严格分开

| 层次 | 含义 | 证据 | 本里程碑 |
| --- | --- | --- | --- |
| **检索** | 给定查询，索引返回的候选与排序是否包含答案 | 冻结检索集（§5.1）；`act/checked` 的 `rank_seqs` | **证明** |
| **呈现** | 答案事件是否实际进入了某次模型请求（原文窗口、文字、`check` 结果） | `control/presented` 与 `act/checked`（P7） | **证明** |
| **使用** | 模型是否读了、理解了、用了 | 档案无法证明；假模型不理解任何东西 | **不声称** |

基线报告与 PR 描述中，任何结论都标明属于哪一层。“呈现覆盖率高”不能写成“它记得”。

### 1.3 P8 结束时

1. **`check` 走一个可校验、可重建的派生索引：** 按相关度选出，按时间呈现。罕见词、标识、长文尾部、被高频话题包围的旧事实都能找到。候选受限、检索词被裁剪、退回逐字扫描时，都在结果中明说。
2. **索引不是记忆库：** 它不保存原文，不被模型写入，不进入快照，随时可以删除重建；`check` 的结果仍逐字取自档案。按 TERMS §2，`check` 是核对档案原文，不是回忆；它自己写下的文字仍是记忆的候选载体，什么值得写、写什么，仍由它决定，程序不替它判断。
3. **一套可复现的长期生活评测：** 两段冻结的 9 周合成生活、确定性的假模型与模拟时钟。整理在模拟生活中由服务自己的计时器真实发生。统计只读档案与呈现记录。
4. **一份基线报告：** 三个对照臂（只有原文窗口 / 原有逐字扫描的 `check` / 索引 `check`），回答 Q1–Q6。

## 3. 工作流 C：派生索引与查档

### 3.1 索引文件

**位置与归属：**

- `<YUVI_DATA_DIR>/index.sqlite`（以及 SQLite 自己的 `-wal`、`-shm`）。
- 只由持有 `service.lock` 的服务进程（或 §3.6 的 `rebuild` 命令）写入。
- 不进入快照（P3 的快照只复制档案），不参与 `verify-snapshot`。恢复出的数据目录没有索引，启动时自动建立。

**内容（结构由 Sol 定，以下为必须具备的信息）：**

| 部分 | 内容 |
| --- | --- |
| 元数据 | `format`（P8 为 `1`）；`tokenizer`（`"p8-grams-1"`）；`scene`、`branch`（索引覆盖的场景，即运行中档案的 scope）；`decode`（运行时 Node 读回 TEXT 的方式：`nul_truncated` 或 `full`，与 P6 的探测相同）；`archive_first_id`（档案第一条事件的 `id`）；`through_seq` 与 `through_id`（已索引到的档案位置及该位置事件的 `id`） |
| 结构表 | 每个**可索引事件**一行：`seq`、种类（`heard` / `said` / `silent` / `wrote`）、`t_recorded`、按运行时解码后的 JavaScript 字符串长度、解码后内容的 SHA-256（可截短到 64 位） |
| 全文表 | FTS5 无内容表：`content=''`、`contentless_delete=1`，`rowid = seq`，一列，值为 §3.2 的词元以空格连接 |
| 词频视图 | `fts5vocab`（`row` 类型），提供每个词元的文档频率 |

**可索引事件**与 P4/P6 的 `check` 范围完全相同：本场景、本分支的 `heard`、`said`、`silent`（包括理由为空的），以及非空的 `inner/wrote`（“非空”按 P6 `nonempty()` 的判定）。其他事件不进入索引。理由为空的 `silent` 只进结构表，不产生词元。

**不变量：**

- **不保存正文副本**（2026-10-23 澄清）：
  - **允许保存的**只有检索必需的东西：
    - §3.2 产生的词元，以及 FTS5 为它们维护的倒排、位置、文档长度与文档频率；
    - 结构表与元数据中的 `seq`、种类、时间、长度、摘要和版本信息。
  - FTS5 在倒排中保存的词元，必然与原文的片段相同（例如标识 `4a87`、短句中的完整词），这不算原文副本。
  - **不得保存**事件正文，或任何可以直接读出正文的副本，具体是：
    - 普通（有内容）或外部内容的 FTS5 表；
    - 存放原文、原文片段拼接或完整词元串的任何表、列或文件；
    - 压缩、编码后的正文。
  - 验收判据见 §5.2 C6。
- **按档案的敏感程度保护：**
  - 词元及其位置足以泄露私人内容，甚至近似还原词序，所以索引的敏感程度视同档案。
  - `index.sqlite` 及其 `-wal`、`-shm`，以及重建时的临时文件：
    - 都在 `YUVI_DATA_DIR` 内；
    - 权限与档案相同（文件 `0600`，目录沿用数据目录的 `0700`）；
    - 不复制到数据目录以外。
  - 索引的内容不进入日志、错误输出、网页与模型上下文。
- 索引可以随时删除并从档案完全重建，不进入快照（见上文“位置与归属”）。以后实现删改事件时，被删改的内容也必须从索引中删除（选用 `contentless_delete=1` 正是为此）；P8 中还没有删改事件。
- 索引不是事实来源。`check` 返回的每一条记录都按 `seq` 从档案读取原文。索引与档案不一致时，以档案为准，并重建索引。
- 索引的任何失败都不阻止档案写入、回合与整理。

### 3.2 切分规则 `p8-grams-1`

对文档与查询使用同一套规范化与分段：

1. **输入：** 按运行时解码得到的字符串，即 P6 的读回语义（Node 22 在 NUL 处截断）。
2. **规范化：** `normalize('NFKC')`，然后 `toLowerCase()`。全角 `ＡＢＣ１２３` 因此等于 `abc123`，`VS Code` 等于 `vs code`。这是与 P4 子串匹配的一处有意的差别：大小写不再区分。
3. **分段**为连续的片段：
   - **CJK 片段：** Script 为 Han、Hiragana、Katakana、Hangul 的连续字符；
   - **词片段：** 其余 `\p{L}`、`\p{N}`、`\p{M}` 的连续字符；
   - 其他字符一律只起分隔作用，不产生词元：空白、标点、符号、emoji、孤立的 UTF-16 代理项。
4. **文档词元：**
   - CJK 片段的每个字作为一个词元，每两个相邻字作为一个词元；
   - 词片段整体作为一个词元。
5. **查询检索词：**
   - CJK 片段只有一个字时取这个字，否则取其全部相邻二元组（不取单字）；
   - 词片段整体取；
   - 按首次出现的顺序去重，最多 32 个。
   - 例：“猫叫什么来着”→ 猫叫、叫什、什么、么来、来着；“露川-4A87”→ 露川、4a87；“鳗”→ 鳗。

**写入 FTS5 时：** 词元以空格连接后写入。FTS5 的分词器不得再拆开或改写 §3.2 的词元：写入后，每个词元都能在 `fts5vocab` 中原样查到，裁剪所用的文档频率才可信（用测试证明，含带变音符号的拉丁词与日文、韩文）。分词器参数由 Sol 定。查询时每个检索词都用双引号包住、按 FTS5 规则转义，用 `OR` 连接。**查询文本从不以 FTS5 语法进入 `MATCH`**（§5.2 C11）。

**规则的版本：** 任何改变文档词元的修改都要换一个 `tokenizer` 值，并触发重建。只改变查询侧的修改（例如裁剪阈值）要换 `act/checked` 的 `meta.rules` 值，不需要重建。

### 3.3 `check` 的选取规则

**不变的部分：**

- 参数 `{ query?, from?, to? }`、参数校验、无效参数的处理、工具描述、时间范围（含端点、本地时区）都与 P4/P6 相同；
- 返回的范围（本场景的 `heard` / `said` / `silent` / 非空 `wrote`）、每条记录的呈现（P4 §2.6：本地时间、作者、逐字原文、沉默的理由）都不变；
- 条数上限 40、字数上限 16,000（JavaScript 字符串长度），整条选入，不截断任何一条。

**常量**（写在代码中，不作为配置项）：

| 名称 | 值 | 依据 |
| --- | --- | --- |
| 候选上限 C | 50,000（按文档频率估计） | 探针：bm25 排序约 0.7 µs/候选，5 万候选约 35 ms；90 万候选约 640 ms |
| 检索词上限 | 32 | 限制长查询的成本 |
| `rank_seqs` 上限 | 100 | 供评测区分“排进前 100 却没被呈现”；`meta` 约 1 KB |
| 同步追平上限 | 2,000 个可索引事件 | 探针：约 8,500 条/秒，约 0.25 s |

**算法：**

1. **没有查询词**（`query` 缺省或为空串）：在时间范围内按 `seq` 从新到旧整条选取，按时间呈现。行为与 P4 相同，改由结构表完成。`mode = "recent"`。
2. **有查询，但 §3.2 得不到任何检索词**（只有标点、符号、emoji 等）：使用逐字扫描（§3.5 的 `scan`，即 P6 现有实现，语义完全不变），并在结果中说明。`engine = "scan"`、`mode = "substring"`。
3. **裁剪检索词：**
   - 读出每个检索词的文档频率；
   - 按频率从低到高、频率相同时按出现顺序排列；
   - 依次保留，直到累计频率将超过 C 为止，最低频的一个总是保留；
   - 其余记为“已裁剪”。
4. **相关度模式**（保留的检索词中最低的频率 ≤ C）：
   - 候选为时间范围内含任一保留检索词的可索引事件；
   - 按 FTS5 的 bm25（`rank`）排序，分数相同时 `seq` 大者在前。
   - **选取：**
     1. 先放入排序第一的一条，以及候选中 `seq` 最大（最近）的一条；
     2. 再按排序顺序整条加入，直到再加一条就会超过任一上限。
   - 这两条总是返回，不论长短：保留 P4 “最近的一条匹配总是返回”，并让最相关的一条不被长度挤掉。
   - `mode = "relevance"`。
5. **常见词模式**（最低的频率也 > C）：
   - 只用最低频的那个检索词；
   - 在时间范围内按 `seq` 从新到旧整条选取，并在结果中说明“这些词都太常见，只按时间从近到远返回”。
   - `mode = "recent"`。
6. **匹配总数** `total`：
   - 相关度与常见词模式下，为时间范围内含任一**实际使用的**检索词的可索引事件数，精确计数，不是估计；
   - 没有查询词时，为时间范围内的全部可索引事件数；
   - `scan` 下为 P6 的子串匹配数。
7. 选出的事件**按时间顺序呈现**，与 P4 相同。

**为什么这样定：**

- 先排序再截断，避免 V1 的“未排序就截断”丢掉相关记录；
- 候选上限与常见词模式保证一个回合不会被低选择性查询卡住；
- 两条必返回的记录让“新近的更正”和“最相关的旧事实”都不会被静默挤掉；
- 新近与旧事实之间的其余竞争不作调整，留给 Q2 测量。

### 3.4 工具结果与 `act/checked`

**工具结果文字**（具体措辞由 Sol 定，满足以下要求）：

- **第一行：** 匹配总数与返回条数（沿用 P4 的“共匹配 N 条，返回 M 条”），并说明怎样选出：“按相关度选出、按时间排列”“按时间从近到远”或“逐字查找”。
- **有以下情况时，各加一句：**
  - 被裁剪的检索词（原样列出）；
  - 常见词模式；
  - 退回逐字扫描及其原因（索引正在建立或不可用；查询没有可检索的字词）；
  - 检索词超过 32 个而只用了前 32 个。
- 其后是记录，格式与 P4/P7 相同。
- 程序生成的文字遵守 P4 §2.6 / D21：不出现档案字段名、`seq`、id，也不出现 `bm25`、`FTS`、`token` 之类的实现词。

**`act/checked` 的 `meta`**（P4 的字段含义不变，P8 起增加以下字段）：

| 字段 | 内容 |
| --- | --- |
| `rules` | 查档规则版本，P8 为 `"p8"`。没有这个字段的旧记录按 P4/P7 解释 |
| `engine` | `"index"` 或 `"scan"` |
| `mode` | `"relevance"`、`"recent"` 或 `"substring"` |
| `terms` | 实际使用的检索词，按 §3.3 第 3 步的顺序 |
| `dropped` | 被裁剪的检索词（可为空数组） |
| `fallback` | 只在 `engine="scan"` 时出现：`"no_terms"`、`"index_building"` 或 `"index_unavailable"` |

`result_seqs` 仍是返回给模型的事件，按呈现顺序（时间顺序）排列；`total` 的含义见 §3.3 第 6 步。工具结果文字必须完全由 `meta` 与所引事件决定，才能精确重建（§3.7）。

### 3.5 维护：追平、校验、重建、降级

| 时机 | 行为 |
| --- | --- |
| **服务启动** | 打开索引，做**快速校验**：<br>① 元数据的 `format`、`tokenizer`、`scene`、`branch`、`decode` 与当前一致；<br>② `archive_first_id` 等于档案第一条事件的 `id`；档案中 `through_seq` 处事件的 `id` 等于 `through_id`；<br>③ 结构表行数等于档案中 `seq ≤ through_seq` 的可索引事件数（可由 P6 的增量状态算出）；<br>④ 按固定规则抽取 256 行，核对它们的长度、摘要与档案一致，且每行在全文表中可以被它自己的一个词元查到。<br>任何一项不符，或文件无法打开、损坏：删除索引文件（只删 `index.sqlite` 及其 `-wal`、`-shm`），从空开始重建。启动不因索引失败而失败。 |
| **追平** | 把 `through_seq` 之后的可索引事件加入索引，在同一事务中更新 `through_seq`、`through_id`。<br>时机：每个回合与每次整理结束后（在同一串行队列中，不在回复的关键路径上）；每次 `check` 之前。 |
| **`check` 之前** | 落后 ≤ 2,000 个可索引事件：同步追平后用索引。<br>否则：用 `scan`，`fallback="index_building"`。 |
| **整体重建** | 从空开始，按 `seq` 分批写入：<br>- 期间服务照常回答（回合、整理、健康检查），`check` 按上一行退回 `scan`；<br>- 完成后执行一次 FTS5 `optimize`。<br>每批大小，以及在主线程分批还是用 worker 线程，由 Sol 决定，须满足 §5.4 P2。<br>进程中断后，重启时按快速校验的结果继续或重来。 |
| **运行中出错** | 索引写入或查询失败时，这次 `check` 用 `scan`，并在标准错误输出一条固定文字（不含路径与异常原文）。不影响档案与回合。<br>- **损坏**（如 `SQLITE_CORRUPT`、`SQLITE_NOTADB`）：删除索引文件，在本次运行中整体重建（同上一行），期间 `fallback="index_building"`；<br>- **其他**（如 `SQLITE_FULL`、文件不可写）：本次运行中把索引标为不可用，`fallback="index_unavailable"`；下次启动按快速校验处理。 |
| **FTS5 不可用**（Node 版本过低） | 与上一行相同：服务照常运行，`check` 用 `scan`。 |

`scan` 就是 P6 的 `archive.search`，保留不变，用于以上降级与评测的对照臂 A1（§4.6）。

### 3.6 维护命令

```
npm run index -- verify [--full]
npm run index -- rebuild
```

- **`verify`：**
  - **逻辑只读**，与 P7 §3.5 的定义相同：不写入档案与索引的已提交内容，不取得 `service.lock`，服务运行时可以执行。
  - 输出 JSON：`status`，以及各项计数与位置（`through_seq`、档案中最后一个可索引事件的 `seq`、结构表行数、期望行数、抽查数）。`status` 的取值：
    - `ok`；
    - `behind`：只是落后，追平即可；
    - `version`：规则或格式不符；
    - `mismatch`：身份、行数或抽查不符；
    - `corrupt`；
    - `missing`；
    - `unsupported`：FTS5 不可用。
  - 默认做快速校验；`--full` 逐行核对全部结构表行的长度与摘要，并对每一行做全文表的可查性检查。
- **`rebuild`：**
  - 取得 `service.lock`，服务运行时拒绝执行，并以非零码退出，什么都不改；
  - 在临时文件中完整建立索引，校验通过后原子替换 `index.sqlite`；
  - 不触碰 `archive.sqlite`。
- **错误输出**遵守 P3 维护命令的约定：只输出固定的诊断文字。

## 4. 工作流 D：合成生活评测

### 4.1 位置与形态

- **位置：** 仓库根目录的 `eval/`。它是研究代码：
  - 不在 `src/` 中，不被产品代码引用；
  - 可以读取构建出的 `dist/`。
- **命令：**
  - `npm run eval -- run <life> --arm <A0|A1|A2> --out <dir>`
  - `npm run eval -- measure <dir>`
  - `npm run eval -- explain <dir> <probe-id>`
  - `npm run eval -- baseline`
  - `npm run eval -- regress`
- **数据：** 全部由脚本生成；生活脚本是仓库中的冻结文件（`eval/lives/*.json`）。不含任何真实对话或个人信息。

### 4.2 生活脚本的格式

一个 JSON 文件，`format: 1`。生成器把它与种子展开成一条确定的时间线（每条负责人消息的时间与文本）。

| 部分 | 内容 |
| --- | --- |
| 头部 | `id`；`seed`；`start`（带偏移的 ISO 时间）；`time_zone`（IANA 名，驱动以它设置子进程的 `TZ`）；`days`；`owner_name`；`writing_policy`（§4.4） |
| `config` | 覆盖的服务配置：`YUVI_CONTEXT_EVENTS`、`YUVI_CONTEXT_WRITING_CHARS`、`YUVI_CONSOLIDATION_IDLE_MS`、`YUVI_CONSOLIDATION_MAX_TOKENS` |
| `rhythm` | 每天的活跃时段，每天的消息数（均值与波动），消息间隔的分布 |
| `gaps` | 没有任何消息的连续日：`[{ from_day, days }]` |
| `filler` | 日常干扰的词表：<br>- 生成器内置一份固定的、按 Zipf 分布抽取的常用汉字与拉丁词表，排名第 1、2、3 的字固定为“的”“我”“是”；<br>- 另有若干**话题池**：`{ id, words, per_day, from_day, to_day }`，按天把话题词放进日常消息 |
| `facts` | `{ id, versions: [{ day, time, text, anchor, correction? }] }`：负责人在指定时间说的一句话；`anchor` 是能唯一识别这个版本的子串 |
| `people` | `{ id, name, mentions: [{ day, time, text, anchor }] }`，结构同上 |
| `probes` | `{ id, day, time, ask, query, targets, tags }`：<br>- `ask`：负责人的问话；<br>- `query`：假模型在这个回合调用 `check` 时使用的参数（对象，与工具参数相同）；<br>- `targets`：标准答案，引用 `facts`/`people` 的版本；<br>- `tags`：`expected_miss`、`high_frequency`、`correction` 等，只用于分组统计 |
| `sanity` | 每周一个“刚刚说过”的检查点：负责人先说一句带唯一暗号的话，下一条消息就问它。用于证明机制没有坏 |

**生成器必须断言：**

- 每个 `anchor`（以及每个暗号）在全部生成文本中，只出现在它被植入的那条消息里；
- 干扰文本不含任何 `anchor`；
- 植入消息不落在 `gaps` 中。

**标准答案的解析：**

- **主答案**：植入那个版本的 `heard` 事件。运行后在档案中按“时间 + 全文相等”唯一确定，找不到或不唯一即报错。
- **携带者**：内容包含 `anchor` 的 `inner/wrote`。只在 `excerpt` 策略下会出现，单独统计，不计入主答案。

Sol 按本节写出 `eval/lives/life-a.json` 与 `life-b.json`。脚本中的数值（话题词、每天条数的波动等）可以细化，但事实、人物、探针、检查点、空白、时段与 `config` 以本节为准。脚本文件随 PR 冻结；以后修改要换 `id`。

### 4.4 假模型

本地 HTTP 服务（扩展现有测试中的假模型），读取同一份生活脚本，对每个请求给出确定的回应：

- **对话第 0 步：**
  - 当前问话是探针或检查点、且对照臂不是 A0：调用 `check`，参数为脚本中的 `query`；
  - 其他情况：从一组不含任何 `anchor` 的短句中按序号确定地选一句回复。每第 25 条普通消息调用 `stay_silent`，理由为空。
- **对话第 1 步**（`check` 之后）：回复固定文本“我查了一下。”，不引用工具结果中的任何内容。
- **整理：** 按写作策略：
  - `none`：输出空文字；
  - `excerpt`：对材料中每条负责人的话，取其前 32 个 Unicode 码点，按顺序以换行连接后输出。不读脚本，不知道哪句是答案。
- **用量：** 按请求中各消息 `content` 的总长度确定地给出 `prompt_tokens`，按输出长度给出 `completion_tokens`。

假模型只是测试夹具。它的行为不代表真实模型会怎样查询、怎样写；这是 §1.2 中“使用”层的问题，不在本里程碑回答。

### 4.5 驱动与模拟时钟

- **进程：** 每次运行在一个子进程中进行，`TZ` 设为脚本的 `time_zone`。子进程内：
  - 用 `createApp` 启动服务（与 P7 相同的入口），数据目录为新的临时目录；
  - 用 `node:test` 的 `mock.timers`（`Date`、`setTimeout`、`setInterval`）控制时间；
  - 假模型监听回环地址。规划探针已验证这个组合可以运行（[探针](research/memory/probes/p8/README.md)）。
  - 探针只推进了约 5 周模拟时间（1,120 个回合，结果文件名中的 `8w` 指循环了 56 个模拟日，每个模拟日实际推进约 15.7 小时）。它是可行性证据，不是 9 周验收。正式要求仍是两段生活的完整 63 天（§4.3、§5.5 E2、E7、E8）。（2026-10-23 澄清）
- **推进：**
  - 按时间线逐条发送负责人消息（`POST /api/messages`），读完 SSE 才推进时钟到下一条消息的时间；
  - 每次推进后等待服务空闲（`app.idle()`）并让出一次事件循环。
- **整理必须真实发生：**
  - 由服务自己的空闲计时器与 P4 的窗口压力触发；
  - 驱动不调用任何内部函数，只使用 HTTP 接口与时钟。
- **只用回环网络**，不访问外网，不使用真实模型。

### 4.6 三个对照臂

| 臂 | 含义 | 怎样实现 |
| --- | --- | --- |
| A0 | 只有原文窗口与文字 | 假模型从不调用 `check` |

### 4.7 统计

`measure` 只读一次运行的 `archive.sqlite` 与生活脚本，输出 `metrics.json`。

**每个探针的每个答案，判定以下各项**（答案指主答案事件 `g`）：

| 项目 | 判定 |
| --- | --- |
| `window` | 在探针回合第 0 步的呈现记录中，`g` 落在 `window` 范围内 |
| `writing` | 第 0 步 `writings` 范围内有 `g` 的携带者 |
| `check` | `g` 在该回合 `check` 的 `result_seqs` 中，并且该 `act/checked` 被下一步的呈现记录引用 |
| `check_writing` | `g` 的携带者在 `result_seqs` 中 |
| `presented` | 以上任一成立 |
| `rank` | `g` 在 `rank_seqs` 中的位置（从 1 起）；不在则为 `null` |
| `reason` | 没被呈现时的原因，见下表 |

**遗漏原因**（机械判定，按顺序取第一个成立的）：

| 原因 | 条件 |
| --- | --- |
| `no_check` | 没有调用 `check`（A0） |
| `outside_range` | `g` 的时间不在 `from`/`to` 内 |
| `substring_miss` | A1：`g` 的原文不含查询子串 |
| `recency_cut` | A1：`g` 含查询子串，但比返回的最早一条更旧 |
| `no_overlap` | A2：`g` 的词元与全部检索词都不相交（换说法属于这一类） |
| `dropped_only` | A2：`g` 只与被裁剪的检索词相交 |
| `common_mode` | A2：常见词模式下，`g` 比返回的最早一条更旧 |
| `budget_cut` | 排序（A2）或时间顺序（A1、常见词模式）在条数上限以内，因字数上限没被选入 |
| `ranked_out` | A2：相关度模式下进入了候选，但排在返回范围之外（`rank` 可能 ≤ 100 或为 `null`） |
| `unexplained` | 以上都不成立。必须为零（§5.5 E6） |

**汇总**（每个臂、每段生活分开给出）：

- **呈现覆盖率：**
  - 按答案的年龄分组：< 1 天、1–7 天、7–28 天、> 28 天；
  - 按渠道（窗口、文字、`check`）；
  - 按标签（`high_frequency`、`correction`、`expected_miss`）。（Q1、Q4）
- **更正对：** 含两个及以上版本的探针中，全部版本都被呈现的比例；呈现顺序是否为时间顺序。（Q3）
- **竞争：** 多版本答案中，旧版本与新版本的 `rank` 分布；`life-a` 与 `life-b` 中同一探针的 `rank` 对照。（Q2、Q4）
- **检索与呈现的差距：** 有词元相交的比例 → 排进前 100 的比例 → 被呈现的比例，以及每级的遗漏原因计数。（Q5）
- **随时间的变化：** 同一事实在不同周被探针问到时的呈现与 `rank` 序列（F1、F2、F3、F5、F11）。
- **文字的消费覆盖：**
  - 每条非空 `inner/wrote` 在写下之后被呈现的次数，按 P7 `writings` 的口径；
  - 从未被呈现的比例；
  - 经由 `check` 被呈现的比例。
- **检查点：** S1–S7 的呈现情况。
- **成本：**
  - 每个回合的请求数；
  - 第 0 步与第 1 步以后请求的 `total.chars` 的均值与 p95；
  - `check` 的调用次数与工具结果字数。
- **不确定的数字：** 墙钟耗时、`check` 实际耗时、运行结束时 `index.sqlite` 的字节数，写进单独的 `timing.json`，不进入 `metrics.json` 与回归比较。

**通用性只到这一步为止：** 判定 `window`/`writing` 时，对呈现清单中任何带 `first_seq`/`last_seq` 或 `seqs` 的部分，都按部分名记录。这样 WP-E 新增的部分（如浮现）不需要改统计代码就会被计入。除此之外不做任何抽象。

**共同要求：**

- 服务启动成功；
- 修复前 `verify` 报告相应的 `status`；
- 修复后 `check` 的结果与在完好索引上的结果相同（按 `result_seqs` 比较），`verify --full` 为 `ok`。

**档案的验收口径**（2026-10-23 澄清，取代原来笼统的“`archive.sqlite` 的字节不变”）：

- **基准：** 注入故障之前一刻的档案，即 `seq ≤ S0` 的全部已提交事件。K7、K12 的基准是换入的档案，或恢复出的档案。
- **四项条件：**

| 条件 | 内容 | 怎样判定 |
| --- | --- | --- |
| A1 既有事件不变 | `seq ≤ S0` 的每一行都与基准逐列相同（`content` 按 `CAST(content AS BLOB)` 比较）；没有缺失、重排或改写；`sqlite_master` 不变；`PRAGMA integrity_check` 为 `ok` | 测试前后各读一次，逐行比较 |
| A2 只追加合法事件 | `seq > S0` 的事件只能来自测试中的正常回合、整理与 P4 的启动恢复。具体是：<br>- 种类都已在 TERMS 登记，每个 `heard` 恰有一个结局；<br>- **索引的维护、校验、重建与降级本身不写任何档案事件**（P8 不新增事件种类）；<br>- 与同一组消息在完好索引上的对照运行相比，新事件的 `class/kind` 序列相同；`act/checked` 只在 §3.4 的选取字段（`engine`、`mode`、`fallback`、`terms`、`dropped`、`rank_seqs`、`result_seqs`、`total`）上可以不同；工具结果不同造成的呈现记录差异也允许 | 与对照运行比较事件序列 |
| A3 没有业务写入时内容不变 | 测试中没有回合或整理的步骤（只有启动、停服、`verify`、`rebuild`、空闲），档案没有新行，A1 成立 | 比较行集合 |
| A4 维护命令只读 | `verify` 按 P7 G6 的逻辑只读口径；`rebuild` 只读档案（同一口径），可以取得 `service.lock`，但不改档案 | 同 P7 G6 |

- **SQLite 的协调变化不算业务写入：** 以下变化都不计入：`-wal`、`-shm` 的创建与变化；`-shm` 中的读标记；正常停服时 WAL 检查点把已提交内容写回主库（逻辑内容不变）。主库字节变化本身不构成失败，以 A1–A3 的逻辑判定为准。
- **不降低完整性要求：** 任何一项中，只要出现以下情况，都是阻塞缺陷：
  - 既有事件的改变、丢失或重排；
  - 无法由正常回合或 P4 恢复规则解释的新事件；
  - 索引操作写入的任何档案事件；
  - `integrity_check` 失败。

### 5.4 性能（100 万事件）

**档案：** P6 生成器增加的 `varied` 形态，100 万个事件，带 §5.1 的植入目标。另用 P6 的 `typical` 形态做同样的测量，只报告，不设门槛：它的词表只有几句重复的话，几乎所有查询都会进入常见词模式。

**测量方法：**

- 计时方式与 P6 §4、P7 G7 相同：服务进程内或 HTTP 两端的单调时钟；
- 每项先预热，再重复 20 次取 p95；
- 数字附原始 JSON 与生成命令；
- 每项都在同一台机器上同时报告 `scan` 的数字，作为对照。

| # | 项目 | 门槛 | 依据 |
| --- | --- | --- | --- |
| P1 | 从空重建（含 `optimize`） | ≤ 5 分钟 | 探针：100 万条、1.12 亿字为 2.2 分钟 |
| P2 | 重建期间的服务 | `/health` p99 ≤ 100 ms（每 100 ms 一次，覆盖整个重建）；期间进行 20 个回合，含 5 次 `check`，全部正常结束，`check` 为 `scan` 并说明 | P6 空闲 `health` p99 为 1.4 ms；分批写入会占用事件循环 |
| P3 | `check` 的检索耗时（索引，热） | **A 类 ≤ 20 ms**：R1、R3、R4、R8、R9、R11、R12、R20、R21、R22。<br>**B 类 ≤ 200 ms**：其余全部，含 R24、R26 与 R28 | 探针：罕见词 < 1 ms；5 万候选排序约 35 ms，常见词模式约 35 ms，加精确计数约 80 ms。P6 `scan`：常见 236 ms、不存在 212 ms、罕见早期约 2 s |
| P4 | 普通回合的程序开销 | p95 < 100 ms（P6 的门槛不变）；与 P7 同机对比的增量如实报告；单次增量追平的最大耗时如实报告 | 探针：增量每批 p95 0.2 ms，自动合并偶尔约 0.4 s |
| P5 | 带完好索引的启动 | 比 P7 同机启动的增量 ≤ 1 s | 快速校验为 O(1) 加 256 次抽查 |
| P6 | 索引大小 | 如实报告（字节、可索引事件数、总字数、词元数）；`varied` 形态下不超过档案大小的 1.5 倍 | 探针：560 MB / 1.12 亿字 |

不能达到时，PR 中给出原始数据与原因，由 Claude 判断是规格前提不成立（按 `AGENTS.md` 修订本节），还是实现问题。

## 6. 实施顺序

一个 PR，内部按以下顺序推进。可以先开 Draft PR；中间不需要逐阶段审批。

1. **切分与索引：** `p8-grams-1`、索引文件、重建与 `verify` 命令、`varied` 形态的生成器；R1–R30 在 5 万规模上通过。
2. **接入 `check`：** 选取规则、`act/checked` 字段、工具结果文字、`p8` 呈现规则与 `presented show`；启动校验、追平、降级；C 与 K 系列。
3. **评测：** 生活脚本格式与生成器、两段冻结生活、假模型、驱动与三个臂。
4. **统计与基线：** `measure`、`explain`、`baseline`、`regress`；E 系列；报告。
5. **规模：** 100 万事件的 P 系列测量；证据包。

如果阶段 3 发现模拟时钟与服务的组合有阶段 1–2 必须配合的改动（例如 `createApp` 的测试选项），直接在本 PR 中完成。

## 7. WP-E 怎样使用本里程碑

| WP-E 需要 | P8 提供 |
| --- | --- |
| `recall`：检索它写下的文字 | 索引的内部查询接口支持 `kinds=['wrote']`（R30），时间范围与选取规则相同。`recall` 只是另一个调用者，返回内容仍取自档案 |
| 线索浮现：用当前输入在前景之外的文字中检索 | 同一接口，加一个排除范围（前景中的 `seq`）。WP-E 自己增加，P8 不预留 |
| 与“只有 `check`”的对照 | 基线报告中 A0、A2 在两段生活上的逐探针结果；同一脚本与种子可以直接重跑 |
| 浮现进入呈现记录后被统计 | §4.7 的统计已按部分名计入任何带范围或 `seqs` 的清单部分 |
| H1（文字能否承担跨天连续）、H2（浮现的增益与闯入）、H7（真实模型会不会自己查） | `excerpt` 与 `none` 两种写作策略的对照；遗漏原因的分布；真实模型实验沿用同一驱动，只把假模型换成真实地址（实验需要负责人批准预算） |
| 新近与旧事实竞争的调整（如果需要） | Q2、Q4 的基线数字。任何调整都要在 WP-E 中与这组数字比较 |

## 8. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| bm25 的长度归一使短句排在前面，长文中的旧事实被挤出 | Q2/Q4 的结果偏向短句 | 这是要测的现象，不在本里程碑调整；基线报告给出长度与 `rank` 的关系 |
| FTS5 自动合并的偶发峰值（约 0.4 s） | 个别回合之后的追平变慢 | 追平不在回复的关键路径上；P4 如实报告最大值；必要时调整 `automerge` |
| 模拟时钟与 HTTP、SSE、SQLite 的交互 | 驱动卡住或结果不确定 | 规划探针已跑通约 5 周的模拟（不是完整 63 天）；E2 双跑校验确定性，E7 检查完整基线的耗时 |
| 指标的效度：假模型的查询由脚本给定，比真实模型理想 | 覆盖率偏高 | 报告中明确写出（§4.8）；真实模型的查询行为是 WP-E 的 H7 |
| 降级路径（`scan`）较少被走到 | 退化时的行为未经检验 | K1、K3、K8、K10、K11 专门覆盖 |
| 最低 Node 版本提高到 22.16.0 | 22.13–22.15 的用户需要升级 | 仍可运行，`check` 降级；README 写明 |
