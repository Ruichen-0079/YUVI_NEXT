## 1. 目标

**要解决的问题。** V2 的档案从 P1 起只有开发对话，没有 V1 中真实发生过的过去。P5 让 V2 拥有这段过去的一份**忠实副本**：

- 原文逐字保留；
- 按真实的时间先后排列；
- 说话者与场所可以辨认；
- 每一条都能追溯到 V1 中的原记录；
- 缺了什么，也如实说明。

**P5 结束时：**

1. **生成一份新的 `dev:v2-dev` 数据目录。** 从负责人确认的 V1 只读副本生成，档案的前段是导入的 V1 交流，之后才是 V2 自己的生活。
2. **对账闭合。** 每条源记录，要么成为一个导入事件，要么在报告中有排除原因。没有静默丢弃，也没有凭空多出的事件。
3. **导入安全。** 导入可重复、可中断，不改动来源：
   - 同一份导出两次导入，结果逐列相同；
   - 中途被杀，不留下半成品；
   - 导出与导入都不写 V1。
4. **可达的部分接入 P4。** 当前架构可以合法触及的那部分过去，即**负责人私下的对话线**，接入 P4 的原文窗口、整理与 `check`。其余部分（群聊、与他人的私聊）完整保存，但要到 C4 有了场景与可见范围以后才可达（§6 决定二）。
5. **它可以先读一遍自己的过去。** 导入的、可达的过去，在投入使用前由它按时间顺序读一遍。读完写什么、写不写，仍由它决定，与 P4 的整理相同（§6 决定三）。
6. **大档案下仍可日常使用。** 档案达到 10 万个事件时，单次回合的程序开销仍在可用范围内。

**这不是记忆迁移。**

- V1 的 Mem0、记忆、Profile、P8 纠正与记忆权威，都是 V1 系统对交流的解释，不是发生过的交流。P5 不导出、不导入它们（理由见 §3.2）。
- 程序不总结、不分类、不判断重要性，也不替它写任何心理活动。

## 2. 调查得到的事实

**依据：**

- V1 仓库：`main` @ `0d894cc7`，Plunge 分支 @ `adff0c70`（未合并）；
- V2 `main` @ `1060c74`；
- 本节只记读代码与实测得到的事实，推断另作标注。

**V1 的消息存储（PostgreSQL）：**

- **`conversation_messages`**（迁移 006、007、014）。每个会话中的 user / assistant 消息，带 `status`（`streaming` / `completed` / `failed` / `cancelled`）、`created_at` / `completed_at` 与 `parent_message_id`。迁移 014 加了 `source_journal_ref`，用来指向同一输入的 Journal 收据。这张表的行可以被更新：流式输出时内容逐步追加。
- **生活日志 `journal_*`**（迁移 013）。`journal_events` 按命名空间编号（`commit_seq`），记录 `recorded_at` 与 `envelope`；`journal_payloads` 保存文本载荷；`journal_event_parents` 记录因果父事件。
- **效果账本 `effect_*`**（迁移 020–023），记录对外发布的意图、尝试与结果。
- **记忆相关的表：** memories、Mem0、profile、p8_corrections 等。
- **角色隔离：** 每个角色使用独立的 schema。

**Alice 的 QQ 生活（Plunge，实际在运行，但未合并）：**

- **时间与来源：** 部署记录始于 2026-10-07/08；人设由 MaiBot 的字段迁移而来。
- **是独立角色：** Alice 与桌面上的 Yuvi 是**两个独立角色**，各有独立的 schema、记忆与会话（`docs/architecture/plunge-alice.md`）。
- **每条 QQ 入站消息都写成一条 Journal 收据**（`surface-receipt-admission.ts`），包括没有寻址 Alice 的群聊消息。收据中有：
  - 文本；
  - 编解码器给出的 `transportFacts`：QQ 时间戳、消息 id、序号、@ 列表、被引用消息的句柄；
  - 发送者（命名空间:QQ 号），以及指向 Person 的绑定（若有授权）；
  - 场所：私聊、群、临时会话。
- **收据本身已经丢掉了的东西（编解码器 `qq-codec.ts`）：**
  - @ 和引用片段从文本中删除，只留在 `transportFacts` 里；
  - 图片变成英文占位文字 `[Image attachment]`，图片本身 `NOT_RETAINED`；
  - **群昵称和群名片不写入 Journal**；
  - `occurrenceTime` 为 `UNKNOWN`；
  - 群成员构成为 `UNKNOWN`。
- **Alice 的发言：** 每条发出的回复写成一条 OUTBOUND 收据，记录 `publicationState`（ACKNOWLEDGED 或 UNKNOWN）与 `causalParents`。生成了却没有发出的回复，只出现在会话表或效果账本中。
- **SILENCE（不回复）不写任何收据。**
- **桌面与网页对话**写在 Yuvi 角色的 `conversation_messages` 中。

**V2 当前的相关事实：**

- **只有 `web` 场景可达。** P4 的原文窗口、整理、文字选择与 `check` 都只看 `scene='web'`（`src/context.ts`、`src/archive.ts`）。
- **默认“每条 heard 都是一个回合”。** 启动恢复会给“没有终结事件”的 heard 补记中断错误；P4 把第一条没有终结事件的 heard 视为进行中的回合，整理与窗口都在它之前停下。如果原样导入大量没有回复的群聊消息，就会凭空产生中断错误，并卡住整理。
- **P4 的积压上限会被触发。** 导入大量未整理事件，再启动服务，积压上限会立刻把它们成批记为“未经整理”。
- **性能（实测）：** 在 10 万个事件的档案上，一个普通回合的程序开销为 3–5 s，带 `check` 的回合为 5.8 s（假模型即时返回）。原因是每次请求都重新扫描并解析全档案。
- **Sol 的 P4 实机报告不在本环境中。** P4 的实验观察来自负责人转述。

**仍需确认的事实（推断，或尚未核实）：**

- Alice 实际部署的 V1 提交，以及部署时是否有未提交的修改；
- 真实数据量；
- Alice 在 Plunge 之前（MaiBot 时期）的 QQ 历史是否存在，存放在哪里；
- ROADMAP §3 说 Alice 在 V1 中“同时有桌面上的语音、声纹识别、形象和看图能力”。但按代码，桌面角色是 Yuvi，不是 Alice。需要负责人确认桌面实际运行的是哪个角色（§6 决定一）。

### 必须完成

1. **发现：只读，在写导入代码之前完成。** Sol 在负责人批准的**恢复副本**（不是生产库）上记录以下内容，并写进 PR：

   - 按来源、种类、场所、月份统计的**计数**（不含任何内容）。

   发现与 §2 不符、会改变 §3.4 映射的，先提出，由 Claude 修改本文件后再实施。
2. **导出。**
   - `scripts/v1-export.sql`：用 `psql` 在恢复副本上执行，全程在只读事务中。
   - 生成一个**导出包**：
     - `manifest.json`：来源说明（由负责人填写：机器、提交、schema、导出时间）、每个文件的 SHA-256、按来源统计的行数；
     - 若干 JSONL 文件：包含 §3.4 映射与 §3.7 来源追溯所需的全部字段。
   - **不导出**记忆、Mem0、Profile、P8 纠正、记忆权威、向量，以及非消息类的 Journal 事件（只统计其数量）。理由有两点：
     - 它们是 V1 对交流的解释。放进 V2 档案，就会经由 `check` 以“原文”的身份回到它眼前；
     - 它们原样保存在负责人的 V1 归档中，研究需要时可以从那里读取，不必进入它的档案。
3. **导入。** 命令为 `npm run import-v1 -- <导出包目录> <导入配置> <目标目录>`。
   - **目标与原子性：** 目标必须不存在，或为空目录。在同级的私有临时目录中构建，校验通过后原子发布，规则与 P3 的 `restore` 相同。失败或被杀时，目标不存在或仍为空。
   - **先校验：** 先校验导出包的清单与 SHA-256，不符则拒绝。
   - **确定性：** 只读导出包与配置，不访问网络，不调用模型。同一输入的输出逐列相同，因此事件 id 由来源确定。
   - **导入配置：** 一个仓库外的 JSON 文件，由负责人提供，只含：
     - 角色在 V1 中的标识（schema 名，以及 QQ 账号）；
     - 负责人的身份：V1 Person id，以及 QQ 号；
     - 纳入的来源范围（§6 决定一）。
4. **映射。**

   | V1 记录                                                                                                         | V2 事件                                                                                                                                       |
   | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
   | 入站文字收据，发送者不是角色自己的账号                                                                           | `experience/heard`                                                                                                                            |
   | 角色的发言，且有发送证据：OUTBOUND 收据（ACKNOWLEDGED / UNKNOWN），或效果账本中的发布尝试；纳入桌面时，再加上状态为 `completed` 的 assistant 消息 | `act/said`。`reply_to` 指向它所回应的、已导入的 heard（来自 `causalParents` 或 `parent_message_id`）；无法唯一确定时为 `null`，句柄留在 `meta.v1` |
   | 只生成、没有发送证据的回复；状态为 `failed` / `cancelled` / `streaming` 的 assistant 消息                        | **不导入**，在报告中按原因计数。不为它们补记错误或沉默                                                                                         |
   | 与某条收据重复的会话行（`source_journal_ref` 相同，或同一条发言的多处记录）                                       | **不重复导入**，在报告中计为重复，并指明保留的那一条                                                                                           |
   | 由角色自己的 QQ 账号发出、但不对应任何一条角色发言记录的消息                                                     | `experience/heard`，actor 为该账号。**不得**记为 `said`：没有它作为 YUVI 发言的记录                                                           |
   | 载荷为 REDACTED / UNAVAILABLE 的收据                                                                            | 照常导入为事件，`content=""`，保留状态写入 `meta.v1`。不还原被删改的内容                                                                      |
   | V1 的 SILENCE、gate 决定、工具、视觉观察、P8 命令等                                                             | 不导入。没有记录的东西不伪造；可统计的，在报告中计数                                                                                          |

   - **`content` 逐字等于 V1 的文本载荷**，包括 V1 编解码器写进去的占位文字，例如 `[Image attachment]`。不翻译，不补全，不还原 @。
   - **每个导入事件都带 `meta.v1`。** 其中至少包含来源表与源 id、V1 命名空间与序号、V1 记录时间；QQ 消息另含原样的 `transportFacts` 字符串与绑定。凭这些字段，可以在 V1 副本中找到原记录。
5. **时间与顺序。**
   - **`t_recorded`：** 导入事件的 `t_recorded` 是 V1 记录它的时间（`journal_events.recorded_at`，或会话行的时间，取哪一列由 Sol 写明）。QQ 的发送方时间戳只保存在 `meta.v1` 中。
   - **`seq`：** 导入事件按 `t_recorded` 排列，同一时刻按 V1 的源顺序排列，`seq` 从 1 起连续编号。
   - **因果优先：** 一条 `said` 永远排在它的 `reply_to` 之后。时间与因果冲突时，保留因果顺序，并在报告中计数。
6. **身份与场所。**
   - **actor：**
     - 负责人（由导入配置中的 Person id 或 QQ 号确定）为 `owner`；
     - 角色为 `yuvi`；
     - 其他 QQ 用户为 `qq:<QQ号>`。V1 没有记录昵称，P5 不猜测。
   - **scene（场所的真实值）：**
     - QQ 私聊：`qq:private:<QQ号>`；
     - QQ 群：`qq:group:<群号>`；
     - 临时会话：`qq:temp:<群号>:<QQ号>`；
     - 纳入桌面时：`desktop`。
   - **branch：** 全部为 `dev:v2-dev`，这是这条开发生活的过去。
7. **导入记录。** 导入事件之后，写入恰好一个 `control/imported`（§4.2）。它记录：
   - 导出包的 SHA-256；
   - 映射版本；
   - 导入范围；
   - 按种类与场所统计的计数，以及按原因统计的排除计数；
   - **负责人私下的对话线 S**：`web`，加上只有负责人与它两方的导入场所（与负责人的 QQ 私聊；纳入桌面时，再加上 `desktop`）。
8. **运行时：导入的过去与 P4 相容。**
   - **以 S 代替 `web`：** P4 中写死 `web` 的地方（原文窗口、整理材料、文字选择、`check`），改为按 S 判断。S 由档案中的 `control/imported` 决定；没有这个事件时，S 就是 `{web}`，行为与 P4 完全相同。
   - **呈现场所：** 来自 S 中 `web` 以外场所的事件，在呈现中注明场所（例如“在 QQ 私聊中”），P4 §2.6 的全部规则照样适用。
     - 场所说明只写在非 `assistant` 的呈现文字里；`assistant` 消息仍然只含它说过的话。
     - V1 的 id、QQ 号、消息句柄与 `meta.v1` 字段，都不出现在呈现文字中。
   - **导入的 heard 不是 V2 的回合：** 启动恢复不为它们补记错误；P4 不把它们视为进行中的回合。
   - **S 以外的场所：** 不进入任何上下文、整理，也不出现在 `check` 结果中，到 C4 再定。
9. **初读：导入的过去先经过它一次。** 命令为 `npm run consolidate-past -- <数据目录>`。
   - **按 P4 的整理合同执行：**
     - 按时间顺序，把 S 中尚未整理的导入对话事件分批交给它整理，每批不超过 N 个；
     - 结果照样写成 `inner/wrote`；
     - 每批都带上它此前写下的文字；
     - 说明文字用 §4.3 的固定文本。
   - **服务锁：** 运行期间持有服务锁，服务不能同时启动。
   - **可续跑：** 进度由档案决定（P4 的 C），被杀后重跑会从断点继续。
   - **失败：** 模型失败时不写事件，以非零退出码退出，并报告已完成的批数。
   - **服务启动的前提：** 只要 S 中还有未整理的导入事件，服务就拒绝启动，错误信息指出这个命令。这样，P4 的积压上限不会把导入的过去成批记为“未经整理”。
10. **性能。** 不改表结构。档案达到 10 万个事件时，达到 §5 E12 的数值。实现方式由 Sol 决定，例如按条件查询，代替全量读取与解析。
11. **隐私与报告。**
    - 导出包、导入后的数据目录与导入报告都不进入仓库或 PR。
    - PR 中只附**计数与哈希**：发现阶段的计数，以及真实导入的对账表。
    - 测试与验收只用合成数据。
    - 进程输出不含消息内容。
12. **登记事件种类。** `control/imported` 已由本 PR 在 `docs/TERMS.md` 登记；关于导入事件的说明，也已写入 TERMS。
13. **测试与说明。**
    - `npm test` 覆盖上述行为，只用合成的导出包，不访问外部网络、真实模型或 PostgreSQL。
    - `README.md` 写明导出、导入、初读的步骤与安全要求。
    - `docs/notes/P5.md` 写明映射的实现选择与发现结果，不超过一页。

### 明确不做

- **不导入 V1 的解释：** V1 的记忆、Mem0、Profile、P8 纠正与记忆权威，作为事件或作为 YUVI 的记忆都不导入。
- **不替它理解过去：** 不摘要，不提取事实，不评分，不设定情绪或关系状态，不生成它没有写过的心理活动。
- **不打开 S 以外的场所：** 不让群聊、与他人的私聊进入上下文或 `check`；不为其他 QQ 用户补全昵称；不推断群成员构成。
- **不还原 V1 已经丢掉的内容：** 不补回图片、@ 与引用。
- **不接触生产：**
  - 不连接、不锁定、不修改生产中的 V1 数据库；
  - 不停止 Alice；
  - V2 不以任何 QQ 身份对外行动。
- **不做通用迁移框架：** 不支持 MaiBot 或其他平台（除非 §6 决定一另行纳入）；不做增量导入，也不并入已有档案。增量导入属于 C6 的切换，到时单独规划。
- **其他：** 不改 `events` 表的结构、触发器与索引；不加 `recall`；不改变 P1–P4 事件的含义。

> 你写下的文字会原样保存。以后对话时，你写下的文字会从最近的一条往前放进你的上下文，总共大约放得下 {chars} 字；放不下的旧文字不会消失，仍可以用 check 查到。一次写下的文字过长时，会在长度上限处停止。
>
> 你写下的文字不会出现在对话中，但{owner}能够查阅档案。原始记录不会因此改变，以后在对话中需要时，可以用 check 查阅原文。

### 4.4 边界

- 遵守 P1–P4 的全部边界，以及 `AGENTS.md` 的不变量。
- **真实数据：** 只有在负责人按 §6 批准后，才能接触真实的 V1 副本；只能在负责人指定的机器上处理。
- **数据库只读：** 导出脚本只发 `SELECT`，并在只读事务中执行。
- **结构不变：** 不修改 `events` 表的结构、触发器与索引，不新增表。P3 的快照、校验、恢复，对导入后的档案照样有效。
- 不修改 `AGENTS.md`、`docs/ROADMAP.md`、`docs/TERMS.md`、`docs/P1.md`–`docs/P5.md`。
- 不新增运行时依赖。导入器不连接 PostgreSQL，只读导出包。

### 4.5 由 Sol 决定

- 导出包中 JSONL 的具体字段与文件划分（须满足 §3.4 与 §3.7）；
- `meta.v1` 的具体结构；
- 导入事件 id 的生成方式（须由来源确定）；
- 同一时刻事件的排序规则；
- 发送证据的具体判定方式（发现阶段核实后写明）；
- 性能实现；
- 代码结构。

## 6. 需要负责人决定

以下三项决定 P5 的输入范围和运行时改动，**交给 Sol 之前必须确认**。另外，按 `AGENTS.md`，P5 接触真实的 V1 副本，需要负责人在本 PR 中明确批准。

**决定一：导入谁的过去。**

- **事实：** 在 V1 中，Alice（QQ，Plunge）与 Yuvi（桌面与网页）是两个独立角色，记忆、会话与 schema 都分开。把两段生活合进同一个 V2 个体，等于程序造出一段从未发生过的、统一的过去。
- **推荐：** 只导入 Alice 的过去，即 Plunge 时期 Alice schema 中的 QQ 交流，与蓝图“v2-dev 是 Alice 历史的一条开发分支”一致。不纳入 Yuvi 的桌面历史，也不纳入 MaiBot 时期（它不在 V1 中，格式另计）。
- **请同时确认：** 桌面上实际运行的是不是 Alice（ROADMAP §3 与代码不一致）。

**决定二：哪些过去在 C2 中可达。**

- **事实：** 按 `AGENTS.md` 不变量 4 与蓝图 N10，内容只能进入听众是其可见范围子集的场景。V2 目前只有负责人的网页场景，没有多场景与可见范围的机制（C4 / P9）。
- **推荐：** 只让“负责人私下的对话线 S”可达，即与负责人的 QQ 私聊（纳入桌面时，再加上桌面），它与网页的听众相同。群聊和与他人的私聊完整导入并保存，C4 起再可达。
- **代价：** Alice 的生活主要在群里。按这个推荐，C2 中能触及的只是其中一小部分；P5 的主要价值，是一份经过核实、随时可以接入 C4 / C6 的过去。
- **另一个选项：** 若希望群聊过去现在就可达，需要先决定跨场景的可见范围，例如以“负责人在该群中发过言”为证据。这相当于提前做 P9 的一部分，我不建议放进 P5。

**决定三：导入的过去要不要先经过它一次。**

- **事实：** P4 的不变量是“经历离开视野之前，要么经过整理，要么如实记下没有整理”。导入的过去从未在它眼前出现过，两种做法都满足这个不变量。
- **推荐：（A）初读。** 用 `consolidate-past` 按时间顺序让它读一遍、自行写下（§3.9）。成本按“每批 N 个事件”估计；以 2 万个事件、N=200 计，约 100 次调用、数百万输入 token（推断）。
  - 理由：不读一遍，它很难知道过去里有什么。P4 的实机实验也看到，它查空时会误以为历史不存在。
- **（B）不初读。** 导入时直接记下“这段过去没有经过整理”（需要另登记一种事件），它只能靠原文窗口里的末段和 `check` 接触过去。
- **补充：** 导入本身对两者相同，因此同一份导入档案的两个副本，可以分别走 A 与 B，用于比较。

## 7. 有意保持开放的问题

1. **它是否把导入的过去当作自己的。** P5 只提供可信的材料。
2. **记忆的形成方式。** 初读一次读完一生，与在生活中逐步整理，形成的东西是否不同。
3. **V1 时期的“自己”。** 那是另一套程序与另一份人设写出的话，它怎样对待；程序不替它决定。
4. **V1 已经丢掉的内容对理解的影响：** 昵称、图片、@ 与引用。
5. **其余过去的可达：** 群聊过去的可见范围与呈现，留给 C4 / P9。
