## 1. 目标

### 1.1 要研究的问题

P8 证明了一件事：只要发出了正确的 `check`，档案中的旧经历可以被准确检索并呈现。

但那是一次明确的档案查询，不是回想。P9 研究两个不同的过程：

- **A. 主动回想（`recall`）：** 她可以自己决定去找自己以前写下的文字。这些文字是她当时的表达与整理，不是程序维护的事实库。是否调用、何时调用，由模型决定。
- **B. 线索浮现：** 当前这句话与她以前写下的某些文字在词元上相交时，少量旧文字不经她请求就进入这一次的上下文。程序只计算可核验的词元关系，不解释这句话的意思、意图或真假。

**要回答的不是“召回率能多高”，而是过去写下的东西怎样参与现在：**

- 什么样的当前线索能带回旧内容？
- 浮现能否改善跨天、跨周的连续性？
- 高频话题会不会反复占据浮现的位置？
- 无关的旧内容造成多少干扰？
- 更正前后的新旧文字如何竞争？
- 模型会不会真的自己使用 `recall`？

**“更多旧内容进入上下文”本身不算成功。** 浮现可能改善连续性，也可能增加噪声、占用预算，或让过时的内容干扰当前判断。负面结果是有效结论。

### 1.2 层次与证据边界

沿用 P8 §1.2 的三个层次，加上 P9 的两条区分：

| 层次 | 含义 | 本里程碑的证据 |
| --- | --- | --- |
| **检索** | 索引给出的候选与排序是否包含某段文字 | `act/recalled` 的 `rank_seqs`；呈现记录中浮现的候选 |
| **呈现** | 这段文字是否实际进入了某次模型请求 | `control/presented`（P7）及其中的 `surfaced` 部分 |
| **使用** | 模型是否注意、理解、采用了它 | 档案无法证明；假模型不理解任何东西 |

- **浮现 ≠ 回想。** 浮现是程序按词元关系把文字放进请求，由呈现记录记录；回想是她的行为，入档为 `act/recalled`。
- **回想到 ≠ 相信。** `recall` 返回一段文字，不表示她同意、采用或认为它准确，也不把它提升为当前事实。

## 3. `recall`：主动回想

### 3.1 工具契约

```ts
recall({ query?: string, from?: string, to?: string })
```

- 参数的含义、校验、时间范围（含端点、本地时区）、无效参数的处理，都与 `check` 相同（P4 §3.4）。
- **工具描述（固定）：**“回想你自己以前写下的文字：返回你写下的、与查询有关的文字和写下的时间。它们是你当时的想法，不一定准确，也不一定是现在的情况；要核对实际发生了什么，用 check。回想会被记录。”
- 工具顺序为 `stay_silent`、`check`、`recall`；只在 `YUVI_RECALL=on` 时提供。
- 对话的第 0–2 步提供全部工具，第 3 步只提供 `stay_silent`（与 P4 相同）。
- 程序**不**根据问题强制或建议调用。

### 3.2 选取

复用 P8 §3.3 的算法，只有以下不同：

| 项目 | `recall` | 说明 |
| --- | --- | --- |
| 范围 | 本场景、本分支、非空的 `inner/wrote`（P8 索引的 `kinds=['wrote']`） | **永远不返回 `heard`、`said`、`silent`** |
| 条数上限 | 10 | 文字通常比对话长，P4 的 40 条放不下 |
| 字数上限 | 8,000（JavaScript 字符串长度） | 约为 `check` 的一半 |
| 必返回 | 排序第一与最近的一条，不论长短（同 P8） | 预算例外不变 |
| 检索词、裁剪、候选上限 C、常见词模式、`rank_seqs` 上限 100 | 与 P8 相同 | 文档频率按全索引计算，与 `check` 一致 |
| 没有查询词 | 时间范围内最近的文字，从新到旧 | 同 P8 |
| 得不到检索词 / 索引正在建立或不可用 | 退回逐字扫描，**只扫非空 `wrote`**，`fallback` 原因同 P8 | 扫描函数增加种类过滤 |

### 3.3 工具结果

- **第一行：** “找到你写下的文字 N 段，返回 M 段。” 后接选取方式：
  - “按相关度选出、按时间排列”；
  - “按时间从近到远”；
  - “逐字查找”。
- 裁剪、常见词、退回扫描、检索词超限的说明，与 P8 §3.4 相同。
- 其后是记录，按时间顺序，用 `record()` 的格式（“{时间} 你写下的文字：…”）。
- 程序生成的文字遵守 P4 D21 与 P8 C12。

### 3.4 `act/recalled`

每次 `recall` 调用写一条事件：

- `actor="yuvi"`，`reply_to` 为当前 `heard`，`model` 必填，`content=""`；
- `meta` 的字段与 P8 的 `act/checked` 完全相同：`arguments`、`result_seqs`（时间顺序）、`total`、`invalid`、`rules`（`"p9"`）、`engine`、`mode`、`terms`、`dropped`、`fallback`、`rank_seqs`、`terms_limited`，以及按 P4 规则附带的 `usage`；
- `result_seqs` 与 `rank_seqs` 中只能出现非空 `inner/wrote` 的 `seq`。

**工具循环：**

- 一步之中有多个 `check` / `recall` 调用时，按顺序执行，各写一条事件；
- 下一步呈现记录的 `step.results` 中，引用为 `{ "recalled": <id> }`；
- 与 `check`、`stay_silent` 的组合规则沿用 P4 §2.5。

### 3.5 它不做的事

- 不把负责人的原话呈现为“你写下的文字”：工具结果只来自 `wrote`。验收逐条核对种类。
- 不把返回的文字标为可信、当前或已采用；档案中不出现这类字段。
- 不因为调用过 `recall` 而改变前景、窗口或之后的选取。改变是 WP-F 的事。

## 4. 线索浮现

### 4.1 何时发生

- **只在对话第 0 步的组装中发生。** 第 1–3 步沿用第 0 步冻结的基础消息（P7），整理请求不浮现。
- `YUVI_SURFACING`：`off`（默认）、`relevance` 或 `recency`。
- 为 `off` 时，请求、事件、呈现记录与 P8 完全相同（§6）。

### 4.2 线索与检索词

- **线索**只是当前 `heard` 的原文，不加窗口、文字或任何程序生成的东西。
- 检索词按 P8 §3.2–§3.3：切分、32 个上限、按文档频率裁剪（C = 50,000）。
- **不浮现**，并在记录中写明原因，的情况：
  - 得不到检索词：`no_terms`；
  - 最低频的词也超过 C（P8 的常见词模式）：`common`。常见词时不做“按时间返回”。
- 规划模拟显示，在生活规模下更严的上限（300–5,000）与 C 几乎没有差别，因此不另设参数（[探针](research/memory/probes/p9/README.md)）。

### 4.3 候选与排除

**候选：** 本场景、本分支、非空的 `inner/wrote`，`seq` 小于当前 `heard`，且与使用的检索词有交集。即 P8 索引的 `kinds=['wrote']` 查询。

**排除（逐条记录原因）：**

| 原因 | 条件 | 理由 |
| --- | --- | --- |
| `foreground` | 文字在本次请求的 `writings` 范围内 | 已经在她面前 |
| `window` | 文字的 `meta.material` 范围整个落在本次请求的 `window` 范围内 | 它摘自的原话已经逐字在窗口中 |
| `budget` | 加入后会超过条数或字数上限 | 见下节 |

排除只看可核验的范围关系，不看内容。

### 4.4 选取与预算

1. **排序：**
   - `relevance`：按 bm25（FTS5 `rank`）排序，分数相同时 `seq` 大者在前，取前 20 个候选；
   - `recency`：按 `seq` 从大到小，取前 20 个候选。
2. **选取：** 按排序逐条考虑，排除 §4.3 的前两类；放得下就整条选入，放不下就记为 `budget` 并继续考虑下一条。选满 3 条、或 20 个候选考虑完时停止。
3. **上限：** 至多 3 条，合计至多 2,000 字（JavaScript 字符串长度）。
   - **没有例外：** 单条超过 2,000 字的文字不会被浮现，只能 `recall`；
   - 这两个值是常量，不是配置项。
4. **不截断任何文字。**

### 4.5 呈现

- **位置：** 一条 `user` 消息，放在原文窗口之后、回合指示之前。浮现每回合都可能不同，放在后面以保持前缀稳定（03 §5）。
- **文字（固定）：** “你想起以前写下的：” 加一个空行，其后是选中的文字，按 `seq` 升序（时间顺序），每条用 `record()` 的格式，条与条之间空一行。
- 程序不说明它们为什么出现，不给分数，不提“检索”“相关度”之类的词（P4 D21、P8 C12）。
- 没有选中任何文字时，不加这条消息。

### 4.6 呈现记录

对话第 0 步的清单（P7 §3.2）在 `rules="p9"` 时：

- **`sections`：** 有浮现时，在 `window` 与 `instruction` 之间加一项：

  ```json
  { "name": "surfaced", "messages": 1, "chars": 1234, "seqs": [101, 205] }
  ```

  `seqs` 按呈现顺序排列。P8 的统计按部分名计入带 `seqs` 的部分，不需要改动（P8 §4.7）。

- **顶层 `surfacing`：** 浮现开启时总是出现，不论是否选中：

  | 字段 | 内容 |
  | --- | --- |
  | `strategy` | `"relevance"` 或 `"recency"` |
  | `terms`、`dropped` | 同 P8 |
  | `reason` | 没有浮现时：`no_terms`、`common`、`no_candidates`、`all_excluded`、`index_building`、`index_unavailable`、`error` |
  | `candidates` | 前 20 个候选的 `seq`，按排序顺序 |
  | `excluded` | `[{ "seq": n, "why": "foreground" \| "window" \| "budget" }]` |

- **大小：** 第 0 步清单不超过 2,500 字节（P7 为 1,500 字节；P9 加约 1 KB），如实报告中位数与最大值。
- **重建：**
  - `presented show` 按 `seqs` 从档案读取文字并重新呈现，必须精确重建；
  - `candidates` 依赖当时的索引状态，`show` 只原样输出，不重算；
  - 验收用独立重建核对（§10.1 C6）。

### 4.7 失败

- **索引正在建立或不可用：** 不浮现，记录 `reason`，**不退回扫描**。扫描在百万规模上约 700 ms，不能每回合执行。
- **选取中的任何异常：** 不浮现，记录 `reason="error"`，在标准错误输出一条固定文字，回合照常进行。
- **档案读写失败**仍按存储失败处理，不被浮现的异常处理掩盖。

## 5. 可见范围

### 5.1 规则

本规格的提交已在 TERMS §2 写入：

> 一段文字的可见范围，取它形成时所读材料中最严格的那个。`recall` 与浮现只返回当前听众可见的文字。

现阶段只有一个场景（`web` / `dev:v2-dev`），整理材料只取本场景的事件。所以实际执行的是：**文字的 `scene`、`branch` 与当前相同**才可见。

以后出现多个场景时，需要在整理时记录材料的可见范围，那是那个里程碑的事。

### 5.2 执行要求

- `recall`、浮现、`check`、退回扫描、无查询词的列表、`total`、`rank_seqs`、`candidates`、`excluded`、`presented show`，**任何一处**都不包含其他 `scene` 或 `branch` 的事件，也不受它们影响：
  - 计数不包括它们；
  - 排序不包括它们；
  - 错误信息不泄露它们。
- P8 的索引只收录档案 scope 内的事件。P9 仍须在读取原文时再次核对 `scene` 与 `branch`，不一致就当作索引与档案不符处理（P8 §3.5 的损坏路径）。
- 文件、日志与错误输出的保护沿用 P8 §3.1。

## 6. 兼容与规则版本

- **兼容模式**（`YUVI_RECALL=off` 且 `YUVI_SURFACING=off`）：
  - 请求、事件、SSE、呈现记录（含 `rules="p8"`）都与 P8 逐字节相同；
  - P8 的 `npm run eval -- regress` 仍逐字节复现 `docs/notes/P8-baseline.json`。
- **`rules="p9"`：** 只要提供了 `recall` 工具，或浮现开启（即使没有选中），呈现记录的 `rules` 就为 `"p9"`。

### 8.1 对照臂

### 8.2 假模型的界限

- 假模型的工具调用由脚本决定：E-R“总在探针回合回想”，E-S 系列“从不调用工具”。
- 因此 E-R 测的是“如果她去回想，她自己的文字能否带回答案”，**不是**“她会不会去回想”。后者是 H7，只能由真实模型回答。
- `excerpt` 的文字只是一种固定的摘抄，不代表真实模型会写什么（H1-r）。
- 报告中逐条写明这些界限。

### 8.3 统计

**在 P8 §4.7 的基础上扩展，不改 P8 已有的口径。**

**每个探针答案的新渠道：**

| 渠道 | 判定 |
| --- | --- |

**新的遗漏原因**（机械判定，按顺序取第一个成立的；`unexplained` 必须为零）：

### 9.4 预算

- 每次运行约 700 个请求；
- 每个请求约 5,000–7,000 字（浮现开启时多至 2,000 字）；
- 按 1 字 ≈ 1 token 计（中文的保守上限）。

| 档 | 内容 | 输入 token 上限 | 输出 token 上限 | 举例费用 |
| --- | --- | --- | --- | --- |

| T2（建议） | H7、H1-r、H2-r：R0、R1、R2 各 2 次 | 30M | 1.2M | 约 $5 |
| T3 | T2 再加完整 `life-a`（每天 40 条） | 不建议在 T2 之前做 | — | — |

- **举例费用的假设：** 输入 $0.3/M、缓存命中 $0.03/M、输出 $1.2/M、缓存命中率 70%。这只是举例，实际单价以负责人选定的服务为准。
- 费用公式：未命中输入 × 输入单价 + 命中输入 × 命中单价 + 输出 × 输出单价。

## 11. 实施顺序、交付与工作量

一个 PR，内部按以下顺序推进，不逐阶段审批：

1. `recall` 工具、`act/recalled`、扫描种类过滤；W1–W11；C3–C5。
2. 浮现的选取、排除、呈现与记录；`p9` 规则与 `show`；S1–S12；V1–V4；K1–K5。
3. 评测：新对照臂、探针策略、新统计与原因、`life-r`、真实模型驱动的护栏；E1–E9。
4. 基线：`baseline-p9`、`regress-p9`、报告；X1–X4。
5. 性能：100 万 `writings` 形态，P1–P5；证据包。

**证据包**按 `AGENTS.md` 与 P8 §9：

- 交付内容与偏离；
- 两个 Node 版本上 `npm test` 的结果；
- §10 逐项自查，标明“实测 / 推断 / 未验证”；
- 性能原始数据与测量命令；
- 基线报告的要点；
- 已知限制；
- 复现命令。

**预计工作量：** 6–7 个 Sol 工作日，不含验收往返。

| 部分 | 工作量 |
| --- | --- |
| `recall` | 1 天 |
| 浮现与重建 | 1.5 天 |
| 可见范围与失败 | 0.5 天 |
| 评测与统计 | 1.5–2 天 |
| 基线与报告 | 0.5 天 |
| 性能 | 0.5–1 天 |

## 12. 与 WP-F 的关系

**不合并成一个里程碑。** WP-F（重整与激活）依赖 P9 的结果：

- 访问历史是什么、浮现的干扰与回声有多大、真实模型是否会回想，都决定激活应当计入哪些访问；
- WP-F 的研究风险高（路线图），合并会让 WP-E 的工程验收等待一个未知的研究结论。

**P9 留给 WP-F 的东西**（只是这些，不建通用接口）：

| WP-F 需要 | P9 提供 |
| --- | --- |
| 访问历史 | 档案中的 `act/recalled.result_seqs`、呈现记录的 `surfaced.seqs`、`act/checked.result_seqs`（`wrote` 部分）；都带时间 |
| 激活作为另一种选取方式 | 浮现的候选流程（§4.3–§4.4）。WP-F 增加第三种 `strategy`，与 `relevance`、`recency` 对照 |
| 对照数字 | P9 基线：集中度、回声、年龄分布、候选到浮现的损失 |
| 前景选择 | P9 不改；仍是 P4 的新近规则，作为 WP-F 的对照 |
