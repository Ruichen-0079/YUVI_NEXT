## 1. 目标

**要解决的问题：** P4 在每个回合、每次整理、每次空闲计时（每秒一次）都调用 `archive.events()`，读取并解码整张事件表，再在内存中过滤。

- 10 万事件时，普通回合的程序开销为 3–5 s（P4 验收实测）；
- 100 万事件时，仅整表解码一次就约 45 s（选型探针）。
- 档案随生活增长，这条路径不可持续。后续工作包（呈现记录、索引、回忆、重整）都要在大档案上测量，它是共同的前置。

**P6 结束时：**

1. **回合、整理与空闲计时的路径上，不再读取整张事件表。** 改为按 `seq` 有界的查询，加上必要的增量状态。
2. **行为不变。** 对同一个档案，发给模型的请求、写入档案的事件、SSE 输出、恢复行为，都与 P4 一致；P1–P4 的验收全部仍然通过。
3. **场景与分支不再写死在各处。** `web` 与 `dev:v2-dev` 只在一处定义，作为参数传给档案读写与上下文计算；不新增场景，不新增配置项。
4. **在 100 万事件的合成档案上，程序耗时有实测、可复现，并与模型耗时分开报告。**

这是一个纯工程工作包：不改变它经历什么、记得什么、怎样呈现。

## 2. 范围

### 必须完成

1. **有界查询与增量状态。** 以下路径不得调用无 `after` 参数的 `archive.events()`，也不得以其他方式读取并解码全部事件：
   - 回合（`turn`，含 `pressure()` 与工具循环中的每一步）；
   - 整理（`consolidate()`）；
   - 空闲计时器的每次检查。

   P4 中这些路径用到的量，都要能在有界的读取下得到：

   | P4 中的计算（`src/context.ts`） | 含义 |
   | --- | --- |
   | `state().dialogue.length` | 本场景、本分支的对话事件（`heard`/`said`/`silent`）总数，决定原文窗口的跳跃式起点 |
   | `state().covered`（C） | `inner/wrote` 与 `control/unconsolidated` 的 `meta.material.through_seq` 的最大值 |
   | `state().pending` / `materials` / `firstPending` | C 之后的对话事件；第一条尚未结束的 `heard` |
   | `state().raw` / `pressure` | 原文窗口与是否需要整理 |
   | `writings()` | 从最新一条往前、整条放入、累计不超过预算的非空 `inner/wrote` |
   | 空闲计时器 | 最后一个对话事件的时间、是否有待整理材料 |

   做法由 Sol 决定（§3.4）。可以是按 `seq` 倒序、带 `LIMIT` 的 SQL；也可以是启动时从档案建立、此后随 `Archive.append` 更新的内存状态；或二者结合。

2. **`check` 保持语义，改为在 SQLite 中执行。**
   - 匹配规则与 P4 完全一致：
     - 本场景、本分支的 `heard`/`said`/`silent` 与非空 `inner/wrote`；
     - 时间范围包含两端；
     - **区分大小写的子串**（与 JavaScript `String.prototype.includes` 一致，空查询匹配全部）；
     - 返回最近的至多 40 条、累计不超过 16,000 字（同 P4 的计算方式），按时间顺序呈现；
     - 如实给出匹配总数。
   - `check` 的最坏情况仍需扫描（罕见词约 0.4 s/100 万事件），这是已知的、由 WP-C 解决的限制。P6 只要求不再在 JS 中解码全表，并如实记录耗时。

3. **场景与分支参数化。**
   - `web` 与 `dev:v2-dev` 在 `src/` 中只出现在一个定义处；
   - `Archive.append` 的默认值、上下文与 `check` 的过滤、`Archive.context()` 都使用这组参数；
   - 不新增环境变量或配置项，不新增场景。

4. **百万事件合成档案与性能脚本**（测试辅助，不进入运行时）：
   - **生成器：** 确定性（给定种子，输出逐字节相同），生成一个合法的 P4 档案。
     - 包含：完整的回合链（`heard` → `reply_attempt` → `said`，`reply_to` 正确）、`silent`、三种 `outcome` 的 `error`、`act/checked`、`inner/wrote`（材料范围前后相接）、`control/unconsolidated`、一条 `control/restored`；
     - 内容为长度不一的中文与英文混合文本；时间跨度约三年。
   - **两种形态：**
     - **(a) 典型：** 约每 200 个对话事件一次整理，文字非空；
     - **(b) 最坏：** 所有 `inner/wrote` 的内容为空（于是“近期文字”的查找没有可停之处）。

     两者结尾都处于“全部回合已结束、整理没有落后”的状态。
   - **性能脚本：** 一条写在 PR 描述中的命令，在两种形态上启动真实服务（假模型），输出 §4 F5 所列指标的 JSON。
   - 生成器与脚本不被 `npm test` 运行（太慢），但 `npm test` 中应有一个用小规模（例如 2 万事件）同一生成器的快速检查。

5. **等价性测试。** 在 `npm test` 中加入差分测试：
   - 在随机生成的小档案上（覆盖整理、整理失败与积压、空文字、长度停止、未结束的回合、窗口起点跳跃、文字超出预算），比较新实现与 P4 实现对同一档案计算出的结果；
   - 比较的对象：原文窗口、`pressure`、待整理材料、文字选择、`check` 的结果与总数；
   - P4 的纯函数可以作为**测试中的参照**保留，不进入运行时路径。

### 明确不做

- 不新增档案索引、表或触发器，不改 `events` 表结构（选型探针显示复合索引反而使查询退化，[06 §1.2](research/memory/06-selection.md)）。如果确实需要，作为修改请求提出（§6）。
- 不新增持久文件（WP-C 才引入 `index.sqlite`）。
- 不改变 `/api/events` 与 `/api/usage`。它们不在回合路径上；网页首次加载读取全部事件、`/api/usage` 扫描全表，在 100 万事件时都不理想，记为后续 P 的候选。
- 不改快照、校验与恢复（P3），不改启动时的完整性检查。
- 不改事件种类、上下文呈现、整理说明、工具定义与任何模型请求的内容。
- 不升级 Node 版本（属于“运行与部署”）。

## 3. 接口与约束

### 3.1 等价的定义

**同一个档案、同一时刻、同一配置下：**

- 发给模型的每个请求的 `messages` 与 `tools`，与 P4 在 JSON 层面逐项相等；
- 写入档案的事件序列（除 `id` 与 `t_recorded` 外）相同；
- SSE 帧序列相同。

时间相关的差异只来自“现在”本身：回合指示中的当前时间、新写入事件的时间。

### 3.2 增量状态的约束（如果采用）

- **只在内存中，不持久化。** 启动时从档案建立；档案是唯一的事实来源。
- **只由 `Archive.append` 更新。** 进程中只有它写档案；单实例锁保证没有其他写者。
- **启动顺序与 P4 相同：** 完整性检查 → 打开 → `recover()`；`recover()` 写入的事件也要反映在状态中。
- **内存占用不随事件数线性增长到“每个事件一份内容”的程度：**
  - 允许每个对话事件或每条文字保留少量数字（例如 `seq`、长度）；
  - 不允许缓存事件内容。
  - 100 万事件时进程 RSS 见 F5。

### 3.3 边界

- 遵守 P1–P4 的全部边界与 `AGENTS.md` 的不变量，以及“依赖与架构选型”一节。
- 不新增运行时依赖；`package.json` 的 Node 要求保持 `>=22.13.0`。
- 不新增 Adapter、Repository、Service 之类的抽象层：改写现有的 `src/archive.ts`、`src/context.ts`、`src/server.ts` 即可。
- 不修改 `AGENTS.md`、`docs/ROADMAP.md`、`docs/TERMS.md`、`docs/P1.md`–`docs/P4.md`、本文件。

### 3.4 由 Sol 决定

- 有界 SQL、内存增量状态，或二者的组合；
- 函数怎样拆分与命名；
- `check` 的 SQL 写法：子串语义须与 `includes` 一致（例如 `instr`）；**不能用 `LIKE`**，它对 ASCII 不区分大小写，并把 `%`、`_` 当作通配符；
- 生成器的具体比例与内容；
- 性能脚本的形式与命令名。

## 4. 验收标准

**执行方式：** 与 P4 相同。Claude 用自己编写的驱动、假模型服务与 SQLite 读取工具，对真实进程和真实命令执行检查；环境为 Linux、Node 22。

**计时方式（F5）：**

- 驱动记录每个回合的四个时刻：
  - T1：收到 SSE `heard`；
  - T2：假模型收到对话请求；
  - T3：假模型发出最后一个字节；
  - T4：收到 SSE `done`/`silent`。
- 假模型立即响应。
- **普通回合的程序耗时** = (T2 − T1) + (T4 − T3)，只统计没有触发整理的回合；**模型耗时** = T3 − T2，单独报告。
- **整理请求构建：** 在窗口压力触发整理的回合中，从 T1 到假模型收到整理请求。
- **`check` 步骤：** 从假模型发出工具调用的最后一个字节，到收到下一步请求。
- **空闲时的响应性：** 空闲期间每 100 ms 请求一次 `/health`，记录响应时间。P4 的空闲计时器每秒读取全表，会让这项在大档案上明显变差。
